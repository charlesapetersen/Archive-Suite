## The readers and their routes

One reader per family, the family's current release (owner call (d), 2026-11-17: versions in one family count as
one). None fits W46.ocr-new-open's frozen collector, which sends one image and one prompt to a vLLM server and
cannot carry DeepSeek-OCR-2's per-request n-gram arguments, CHURRO's system-message preset or MinerU's two-step
client. So each reads in process (`sherlock/family-coverage/family_run.py`, on new-open-boxes' runner), with the
open sweep's limits: greedy, one reading a page, at most 8,192 new tokens in a 16,384-token context, the page's own
JPEG bytes, thinking off, the three-page pilot gate first.

- dots.ocr rather than its successor dots.mocr: same family, and the prompt file the card names is dots.ocr's.
  MinerU2.5-Pro-2605 rather than 2509: the family's current release, and Apache-2.0 where 2509 is AGPL.
- The prompts were transcribed on the Mac with no network (two through a web summary); the setup job reads each from
  the model's own package or file and the source wins (`prompt_check` in each `prepared.json` records which). Chandra
  has no transcription (its prompt is an f-string over a tag list): if its package cannot be read, Chandra is skipped.
- Settings that differ from a card, kept for comparability: temperature 0 (olmOCR's pipeline uses 0.1 with retries,
  Chandra's retries rise from 0); 8,192 new tokens (dots.ocr's card allows 24,000, Chandra's 12,384), so a dense
  page that needs more is a cap and scores 0, as it did for every earlier reader.
- The context is 16,384 tokens unless the model's own config allows less (`family_run.model_len`): DeepSeek-OCR-2 and
  MinerU2.5-Pro have 8,192, so on those a long page has fewer than 8,192 tokens for its reply.
- MinerU's client reports no finish reason; a block cut at its limit raises in the client, so that page is an error
  record and scores 0, as a cap does.
- `raw` in each record is the reduced text, which the scorers read as a native reply; `model_raw` is the reply as
  written and `boxes` the blocks where the format has them (dots, DeepSeek, MinerU), for later placement work.
- A batch that raises is read again page by page; a page that still raises is an error record (scores 0) and the
  run goes on, unless the engine died or every page of the batch failed: then the run stops, and a resubmitted run
  reads those pages again.
- Adversarial review (Opus subagent, 2026-11-17) found ten defects before hand-over, all fixed in checkpoint 2: the
  two 8,192-token contexts (both would have failed at load), a dead engine recording the rest of a set as zeros,
  olmOCR's message order and scale, dots.ocr's image tokens, setup failures cascading to every model and a rerun
  reusing a stale candidates file, no processor check on the CPU node, and two reducers dropping text (olmOCR now
  reduces only its tables; dots falls back to the text values). One stays for scoring: CHURRO's pilot3 includes one
  page outside its 455 (`ocrd__aepinus_bekentnis_1548…_0007`, an OCR-D page FarmShare already read), so its folder
  will hold 456 records; drop that page from the 455 row before joining the FarmShare 440.

## Size and necessity review (owner rule 2026-10-22; read before submitting)

1. **The question and the decision it could change.** Whether a reader from a family never measured changes a
   profile's reading pick on the owner's 96 or a stratum's on the 895 (answered and strict NES, paired intervals
   against Qwen3.6 27B and LightOnOCR-3 4B, as W46.ocr-new-open scored). In particular: Chandra-2 and dots.ocr against
   Qwen3.6 27B on print and hands, olmOCR-2 as the cluster reader the literature used at scale, MinerU2.5-Pro's
   built-in layout against the region-first newspaper route (`W46.layout-partition-fix`), DeepSeek-OCR-2 as the small
   DeepSeek reader whose relative Unlimited-OCR scored 41.5 strict. And whether CHURRO-3B, the best cluster route on
   seven historical strata, also leads on the English hands (L1, L2) it was not trained on, which would make it a
   cluster profile's hand reader (C-ocr item 5).
2. **Why results in hand do not settle it.** None of the five has read a page of either set. Literature figures
   (C-ocr claims 14-24) are on other material and disagree with each other (olmOCR-2 last on columns, first in a
   17,774-page production run). CHURRO's FarmShare run read only the 440 historical pages it was trained near; its
   96 reading (89.09) is there, the 455 modern public pages are not.
3. **Size.** Twelve jobs: one CPU setup (prompts, about 43 GB of weights to `$HF_HOME`, MinerU's overlay venv, import
   checks; exits before any GPU job if no model is ready), then per model the 895 on one card afterok and the 96 afterok
   that (CHURRO: its 455 only). Estimate, from the nearest measured runs: Infinity-Parser2-Pro (35B-A3B, two cards) read
   the 895 in about an hour through the same 16-request batching; these are 1.2-8 B on one card, so about an hour for
   each model's 991 pages, half that for MinerU (its card's 2.1 pages a second on an A100) and for CHURRO's 455; with
   load and capped pages about 9 GPU-hours expected. Reserved 8 + 8 + 8 + 8 + 5 + 3 = 40 GPU-hours, generous because
   none of these routes is measured and a timed-out run is resubmitted (the runner resumes; a page read is not read
   again). The pilot gate is three pages, all answered and uncapped, or the model stops before its set. Smaller would
   not do: the both-sets rule (owner, 2026-10-20) needs the 96 and the 895, and the paired comparison needs the same
   895 pages every other open reader read; the families differ by stratum (layouts, hands, scripts), which a
   subsample of the 895 would leave with a handful of pages each. CHURRO already runs on its subset only.
4. **Verdict: useful now.** The owner filed it on 2026-11-17 as the measurement the pipeline review lacks, and two
   picks wait on it being known (the cluster profile's reader and hand reader).
