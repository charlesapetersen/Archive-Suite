## What failed and why the fix holds

Jobs 52765255 (DeepSeek-OCR-2, 895) and 52765258 (MinerU2.5-Pro, 895) died 1 min in, at `LLM()` construction, with
`ValueError: NGramPerReqLogitsProcessor is not a subclass of vllm.v1.worker.gpu.sample.logits_processor.LogitsProcessor`
(MinerU: `VllmV1NoRepeatNGramLogitsProcessor`), raised from `InputProcessor._build_logits_processors_params_validator`
(logs in the parent's artifact, `scratch/logs/slurm-895-*-5276525[58].out`). Their 96 jobs were cancelled afterok.
They failed before `cache-contract.json` was written, so their scratch folders hold no contract or readings that a
rerun would collide with, and setup leaves their `ready` prepared.json alone (no download, no check again).

Read from vLLM v0.31.0's source on 2026-11-26 (GitHub, tag v0.31.0), not from a summary:
- `envs.py`: `VLLM_USE_V2_MODEL_RUNNER` is `maybe_convert_bool(os.getenv(...))`, i.e. `bool(int(value))`, so `"0"`
  is `False` (not a truthy string). Env values are read lazily; the cache is enabled only after engine start, so
  family_run's import of the processor module before `v1_runner()` sets the variable does not freeze it.
- `config/vllm.py` `use_v2_model_runner`: an explicit env value wins (after HiSparse and watermarking, neither used
  here); unset, it picks v2 unless a listed feature forces v1, which is why these two loaded v2.
- `v1/engine/input_processor.py`: with `use_v2_model_runner` False the validator is the v1
  `validate_logits_processors_parameters`, which takes `vllm.v1.sample.logits_processor.LogitsProcessor`
  subclasses; DeepSeek's `NGramPerReqLogitsProcessor` (an `AdapterLogitsProcessor`) is one.
- The engine core is spawned (`VLLM_WORKER_MULTIPROC_METHOD=spawn`) and inherits the variable set in `os.environ`.
So the vLLM pin the item names as a fallback is not needed unless the pilot fails at load again; the pilot gate costs
about a minute if it does.
