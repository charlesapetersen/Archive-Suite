# W46.ocr-new-open-sherlock — item notes

Claimant notes for the open item (SUITE_TODO.md → W46.ocr-new-open-sherlock). Mac side done 2026-10-31: one Sherlock

## The reader

`infly/Infinity-Parser2-Pro`, pinned at revision `b27d470100514329fc6439aada8f16ccea5f9e2a` (Apache-2.0, ungated):
a document-parsing fine-tune of Qwen3.5 35B-A3B (`Qwen3_5MoeForConditionalGeneration`, the architecture vLLM 0.31
already served as Qwen3.6 35B-A3B), 35.1 B parameters, 70.2 GB of BF16 weights in 15 shards. Its card serves it on
vLLM with `--trust-remote-code` and tensor-parallel 2; it reports 87.6 on olmOCR-Bench and 74.3 on ParseBench, and
the gap audit (R7) lists it as the best open reader on columns and hands in Reading the Archive.

Prompt: the package's `doc2md` prompt (`PROMPT_DOC2MD` in `infinity_parser2/prompts.py`), Markdown out, because the
scorers read text; the default `doc2json` returns boxes and categories in JSON that would need reducing first. The
candidates file holds a transcription taken from the GitHub source on 2026-10-31; the setup job downloads the
`infinity-parser2==0.4.0` package (the release current on 2026-10-31) from PyPI and uses the package's string where the two differ, recording which it used
(`prompt_source.py`, `prompt_check` in prepared.json; tests in `test_prompt_source.py`).

Settings: W46.ocr-new-open's harness unchanged (vLLM 0.31.0, context 16,384, temperature 0, thinking off, 8,192
output tokens, eight requests at a time, the frozen collector), except tensor-parallel 2, which the settings contract
records. The card's own 65,536 context and 32,768 output tokens are not used, so the reading is comparable with every
other open-sweep row; a page that hits 8,192 tokens is a cap, as for the others.

FarmShare (two L40S) is not used: Sherlock is this project's cluster (owner, 2026-10-22), and FarmShare needs the
owner's approval for a run.

## Size and necessity review (owner rule 2026-10-22; read before submitting)

1. **The question and the decision it could change.** Whether a Sherlock-class open reader beats Qwen3.6 27B fp8,
   the open incumbent (63.3 NES on the 895, 71.0 answered-only; 95.25 on the 96), on answered-only and strict NES
   with paired intervals on both sets. It decides the cluster profile's open reader in Phase 4 (owner, CLAUDE.md:
   this item stays useful now because many users of the kit will have a cluster like Sherlock). Its hands and
   columns lead in Reading the Archive is a direct claim on L1, L2 and L9, which are where the incumbents differ.
2. **Why results in hand do not settle it.** Nothing has read a page with it. The same base family's general
   model (Qwen3.6 35B-A3B fp8, 63.9 on the 895) says what the base can do, not what the parsing fine-tune does;
   W46.ocr-new-open's three readers changed no pick, which is no evidence about a model trained for this task.
3. **Size.** Three jobs: one CPU setup (downloads 70 GB to `$HF_HOME`, checks the prompt), the 895 on two cards
   (the harness's three-page pilot gates the full run inside the job, so a broken server or empty reading stops
   at three pages), the 96 afterok. There is no Mac pilot: the BF16 weights do not fit the 18 GB Mac, and the
   in-job pilot is the gate. Estimate from the nearest measured run: Qwen3.8 27B fp8 (dense) read the 895 in
   10,052 s on one card, most of it in 102 pages that ran to the 8,192-token cap; a 3B-active MoE decodes several
   times faster, so the 895 should take about an hour on two cards (about 2 GPU-hours) and the 96 a few minutes
   plus a model load, about 3 GPU-hours in all. Reserved: 2 × 6 h + 2 × 2 h = 16 GPU-hours. Smaller would not do:
   the rule that both OCR sets are run (owner, 2026-10-20) needs the 96 and the 895, and the paired comparison
   needs the same 895 pages every other open reader read; the 96 alone is a few minutes, and the 895 is the bulk.
4. **Verdict: useful now** (owner, CLAUDE.md "Cluster work runs on Sherlock" names this item as useful now).

## Hand-over

- Pack (Mac): `$AGENT_STATE/artifacts/new-open-sherlock-20261031` (kit files only, about 50 KB; built by
  `ArchiveProcessor/scripts/segbench/sherlock/new-open/infinity-pack.sh`, dry-run clean). Manifest:
  `ArchiveProcessor/scripts/segbench/sherlock/packs/W46.ocr-new-open-sherlock.json`. Submit, owner session only:
  `bash "$GROUP_HOME/$USER/archive-suite/new-open-sherlock-20261031/support/sherlock/new-open/infinity-submit.sh" "$GROUP_HOME/$USER/archive-suite/new-open-sherlock-20261031"`
- Inputs are W46.ocr-new-open's on Sherlock scratch: `$FS_ROOT/new-open-895` and `new-open-96` (the key
  `infinity-parser2-pro` is added beside the seven earlier ones; their records are not touched),
  `open-sweep-20261019` (the 895's pages, pilot, runner and collector) and `truth96-20261020` (the 96's). The
  manifest's `requires` lists them, so the batch's path check leaves the pack out if scratch has lost them. The
  submit script also appends the pair's ids to `$FS_ROOT/new-open-jobs.tsv`, as W46.ocr-new-open's setup did.
- The setup job only prepares (`NEW_OPEN_SETUP_ONLY=1`): the GPU pair is chained by the submit script, so the
  batch holds, releases and collects all three, and the setup job fails if the model was recorded as skipped, so
  no two-card job starts for nothing.
- Results: each GPU job copies its finished session folder to
  `$GROUP_HOME/$USER/archive-suite/sherlock-results/new-open-sherlock-20261031/{895,96}/infinity-parser2-pro/`
  (best effort); the collect job also copies both scratch session folders, the Slurm logs and `jobs.tsv` under
  `scratch/`, so a failed run comes home with its status and vLLM log.
- If the 895 job fails at server start (a two-card vLLM start has not been run on Sherlock before), its log is
  `scratch/logs/slurm-895-<id>.out` plus the vLLM log inside the session folder in scratch; the 96 never starts.
