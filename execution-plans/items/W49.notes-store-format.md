## What the store is today (read)

- A plain folder. The default is `Application Support/ArchiveNotes/Store` inside the app's sandbox container
  (`Store/RootFolderStore.swift:38-43`). That folder is hidden from the user, has no Finder presence and is not
  where anyone would back up or sync from.
- Inside: `.archive-suite-root.json` (kind `notes`, a GUID), `items/<uuid>/<Title>.md` with its `assets/`,
  `organization.json` (a mirror of the folder graph), `Trash/<uuid>/` (`Store/NoteStore.swift:99-105, 221-242`).
- The search index (SQLite FTS5) lives in the container, not the store, keyed by the marker GUID and path
  (`Core/NotesModel.swift:258-298`). It is a rebuildable cache; the files are the truth.
- File ▸ Choose Store Folder… adopts a folder where it lies: one with a `notes` marker, one with an `items/`
  folder, or one that holds only dot-files (a new store starts there). It refuses Reader archives, folders inside
  a granted archive or under a readable marker, and anything else (`Store/StoreFolderChooser.swift:88-123`).
  The choice takes effect at the next launch, through a security-scoped bookmark.
- A single-library app: two `Window` scenes, no `NSDocument`/`DocumentGroup`, no document types, no package
  type (`ArchiveNotesApp.swift`, `Info.plist`). Saves and deletes go through `NSFileCoordinator`, written so an
  outside editor or sync client can share the files; the KNOWN_ISSUES entries assume a hand-editable store.
- Sandbox: user-selected read-write and app-scoped bookmarks (`ArchiveNotes.entitlements`).

## What a package would be

A folder with its own extension (say `Research.archivenotes`) whose type Notes declares as a package
(`UTExportedTypeDeclarations` conforming to `com.apple.package`, plus a document type with Notes as editor).
Finder then shows it as one object with Notes' icon; double-click opens Notes; "Show Package Contents" opens it
as a folder. The inside can stay exactly as it is today. "Bundle" and "package" mean the same thing for this
purpose: an app or framework bundle has a fixed Apple layout, a document package is ours to define.

Two ways to build it:
- **A library package** (the Photos Library pattern): the single-window app stays as it is. File ▸ New
  Library… (a Save panel, the user names it and picks where), File ▸ Open Library… (an Open panel that shows
  packages as files), double-click in Finder. The bookmark, the container index and every store rule stay.
- **A document-based app** (`DocumentGroup`/`NSDocument`, one window per store). A rewrite of the app's shell
  for no gain the owner has asked for; the index, the Extracts window and the archive grants are app-wide, not
  per-document. Not recommended, and left out of the options below.

## Folder against package, point by point

| | Folder (today) | Library package |
|---|---|---|
| **Sandbox access** | Open panel on a folder; bookmark | The same: an Open or Save panel grants the whole package; same bookmark. No new entitlement. |
| **Finder** | A folder of UUID folders; easy to open, rename or move files inside by accident | One named object, Notes' icon, double-click opens it; the inside is one step away (Show Package Contents) |
| **Moving, copying, backup** | Works; nothing marks the folder as a whole | Works; Finder, Time Machine and AirDrop treat it as one item (AirDrop: unverified) |
| **Sync (iCloud Drive, Dropbox, Google Drive)** | Plain files, per-file sync | Also plain files inside. iCloud Drive syncs packages; web and Windows clients show them as folders (unverified). Conflicts land per file in both cases. Evicted (cloud-only) files need the same handling either way; Notes has none today. |
| **Other editors (Obsidian, a text editor, git)** | Open the folder directly | Their Open panels see a single file unless they navigate inside; git and Terminal see a folder. The `.md` files stay plain and editable. |
| **Spotlight** | The `.md` notes are indexed as text files | Files inside a package are generally not shown in Spotlight results as separate items (unverified); Notes' own search is unaffected |
| **Archive identity** | The `notes` marker inside; adoption by contents (marker, `items/`, or empty) | The marker stays; the extension adds a second, visible sign. "Adopt an empty folder" and "adopt a legacy `items/` folder" go away: a store is made only by New Library… (no migration: nothing to migrate) |
| **Inside a Reader archive** | The Reader, Processor and ArchiveCore walks would descend into it and see its assets | **Already skipped**: `CorpusWalker`, `CorpusWatcher`, `ContainerTree` and the Processor's tree all use `.skipsPackageDescendants`/`isPackage` (read). Only on a Mac where Notes' type is registered; elsewhere it is a folder again. |
| **Default location** | The hidden container folder | Could be a visible `~/Documents/Archive Notes.archivenotes`, made by a first-launch Save panel (the sandbox cannot write `~/Documents` unasked), or the container as now |
| **DEVONthink import (on hold)** | The plan writes `items/`, `assets/`, `organization.json` into a fresh store root and adopts it | Unchanged inside; the fresh root is a package. The import plan's own warning applies: the shape should be settled before 7.5 GB lands in it. |
| **Cost** | Nothing | About an M item: the type and document declarations, New/Open Library replacing Choose Store Folder…, `openURL` handling, the chooser checks, tests on scratch packages, the Reader's chooser refusing a `.archivenotes` by type |

## The ungranted-folder case (the behaviour waiting on this note)

Neither format fixes it alone. The sandbox gives Notes the picked item, not its parents, whether the item is a
folder or a package, and `StoreFolderChooser.check` looks for a parent marker with `fileExists`, which answers
"no" both when there is none and when it cannot look. So:
- **Store inside an ungranted archive.** A package changes what happens: the store is a named object made on
  purpose (no empty folder is adopted silently), and the Reader and Processor walks skip it. Notes still cannot
  tell that the place is inside an archive.
- **Choose Archive Folder… on a subfolder of an ungranted archive** (gives that subfolder an identity of its
  own). Untouched by the store's format.
- What closes both is the question the accepted-issues sheet proposed: when a parent cannot be read, ask "Is
  this folder inside an archive?" and offer Choose Archive Folder… on the archive's top first. A build would
  first measure on a scratch tree whether the sandboxed app can tell "no marker" from "cannot look" (a `stat`
  error, `EPERM` against `ENOENT`); if it can, the question appears only when Notes really cannot see, which is
  every pick outside a granted archive in the shipping app.

## Options for the owner

1. **Keep the folder**, and add the "inside an archive?" question to both choosers. Smallest change; the store
   stays an ordinary folder for other editors and Spotlight.
2. **Make the store a library package** (`.archivenotes`, single-window app unchanged, New/Open Library…,
   double-click opens it), and add the same question. One object in Finder that the other apps already skip;
   the notes stay plain Markdown inside, but other editors reach them through Show Package Contents.
3. **Option 2, and also move the default store out of the hidden container** to a library the user makes and
   sees (first-launch Save panel, `~/Documents` offered).

Recommendation: **3**, before the DEVONthink import. The store is the owner's research; it should be a thing he
can see, name, back up and move as one item, and the suite already treats packages as off-limits to its walks.
The cost is that Obsidian-style editing of the files needs one extra step, and Spotlight probably stops listing
notes one by one. If plain-folder editing in other tools matters more than that, option 1.
