# W49.reader-sender-row-check — what the check found (2026-11-19)

Read from the code at origin/main 5eb2f8c3; nothing built or run.

- **Where the names feature writes.** `EntityExtractor` (Processor `Tagging/EntityExtractor.swift`) puts sender,
  recipient and sending place only in the JSON sidecar's `entities` object (`EntityResult.sidecarObject`), each name
  with `evidence` (quoted, with the quote, or inferred, with why) and a confidence; an empty field holds one
  `"Unknown"` entry. Never in Finder tags, never on page 2: the page-2 header lines are Document date, Sent with,
  Date evidence, Kind, Document kind, Title, Byline, Publication, Publication date and Recipient place
  (`ExtractedContent.swift`), no sender or recipient.
- **Where the feature did not run**, the sidecar keeps the tagging call's `author_name` / `recipient_name` /
  `author_location`, with the sender left out when the text is Apple Vision's (`EntityRunPolicy.sidecarTags`).
- **When the sidecar exists.** `enableSegmentJSON` defaults to on (`SettingsLayerStore`), so Process Files writes
  `<name>.json` beside the PDF and Live Capture writes it in `JSON Output` beside it. Box and folder photos get none.
- **The feature runs** only when the collection ranks names, on correspondence formats (letter, memo, telegram,
  …), never on a Local Agent plan, and the sender is withheld on Apple Vision text (`EntityRunPolicy.decide`).
- **The Reader already parses it.** ArchiveCore `ZoteroSidecar` (`locate` + `parse`) reads exactly these keys for
  Selection ▸ Export to Zotero (W47.ct-zotero). So the KNOWN_ISSUES line "the Reader does not read the JSON
  sidecar" is true of the Inspector only.
