## Necessity and size review (2026-10-25)

1. **Question and decision:** can an oracle table region or cell improve GLM-OCR or
   Qwen3.6-27B field recovery on handwritten L4 registers and the owner's tables?
   A positive result could justify an L4/table-specific crop route in the Mac/open,
   cluster and hybrid profiles (R2/R7/R8); detector cost/accuracy would still be separate.
   The immediate question is smaller: can these readers follow the shared coordinate
   and JSON instruction at all? GLM's native prompt is different, so this capability
   check precedes any claim about cropping. No app default changes in this pilot.
2. **Why existing results do not settle it:** the parent has detector regions/tiles,
   no cell boxes/truth and no table-only control. Page NES merges headings and entries.
   Its table-labelled owner subgroup includes six pages without front-side tables.
   Fresh whole-page field controls use the same prompt as table/cell requests; parent
   native-prose NES is context only. The borrowed forms metric split is adapted, not
   a claim to reproduce an unreleased medical-forms benchmark.
3. **Smallest useful run:** one L4 page (`si__NMAAHC-007630087_00447`) and one owner
   page (p024), 8 selected fields each, both required input sets. Two readers span the
   small native OCR route and the stronger general reader named by K test 8. No other
   reader, detector, paid or subscription arm. Each reader makes 20 sequential requests:
   2 whole + 2 table + 16 cell; 40 total. Three jobs: one CPU stage (2 CPUs/4 GB/10 minutes),
   two one-GPU pilots (8 CPUs/64 GB/one hour each, 48 GB or 80 GB GPU), dependent on stage.
   Each GPU job copies its own receipts/runtime/server log back to GROUP_HOME on exit.
   A smaller single-set check would miss either handwriting or the owner's print;
   more fields/pages before prompt capability is known would spend without an answer.
4. **Timing evidence and limit:** parent crop receipts on exactly these two pages
   contain 45 requests per reader across its three arms. GLM mean 0.716 s, max 4.648 s;
   Qwen mean5.667s,max98.597s including 2 failures (43 successful mean 1.786 s).
   Using the all-outcome means gives about 0.036 GPU-hours for 40 serial requests,
   **only a proxy**, excluding startup and with another prompt/crop distribution.
   The new two-page run is itself the timing pilot; its Slurm elapsed time and receipts
   must replace this proxy before expansion. Hard allocation ceiling 2 GPU-hours.
   The 9-page/72-field bank (180 requests) is frozen but is **not scheduled**; neither
   L4's 80 pages nor all original 12 owner labels are proposed as a full sweep.
5. **Verdict: useful now as this bounded capability pilot.** If either reader ignores
   coordinates/schema, record that limitation and redesign/stop that arm; do not call
   its parse failure an OCR crop loss. No automatic full run follows. Inspect coverage,
   raw replies and filled-field accuracy even if schemas are valid, then review necessity
   and measured GPU-hours again before using the rest of the bank.
