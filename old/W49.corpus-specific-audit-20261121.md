# What Archive Suite carries for the pre-app archive

Source audit at `3653778f`, 2026-11-21. The clearest migration candidates are the Red/Purple meaning, the two named archive trees and their filename matching, and the batch job for reading labels in existing material. Keep the suite's tag and PDF formats, ordinary folder-tree intake, live label reading, and a way to reuse vetted OCR. Treat the owner's layout and interpretations as inputs to a one-time adoption tool.

**Rough size.** The main backfill implementation spans **935 physical lines** across its model, sheet and ArchiveCore scanner/proposal code (454 + 266 + 215). Reader's named layout and the shared JPEG matcher span another **265** (57 + 208). About **1,200 lines** in those five files support the two largest adoption workflows, including reusable review, safety, and indexing code. The literal owner-specific policy is on the order of tens of Swift lines, spread across view, parser and root-selection branches. Its reach is larger than its size. These are file counts including comments and blank lines. Actual retirement depends on the decision to keep a general backfill, and on replacement source-link support. The count excludes shared tagging, ordinary OCR and re-tagging, viewer rendering, tests, docs and benchmark scripts.

## One-time adoption scope

1. Inventory a scratch copy of representative source trees, keeping original paths, identities, tags and source-page information. Produce a dry-run manifest of proposed types, dates, subjects, container runs and original associations, with the rule and evidence for each decision. Route ambiguous pairings, mismatched type evidence, duplicates, absent sources and uncertain dates to review.
2. Establish JPEG associations using the existing tools as evidence. The historical benchmark records 6,789 mirrored pairs and 65,132 unique stems among 102,478 PDFs. More permissive number, folder and image rules add candidates, with 9,885 PDFs still unmatched in that report. These are historical benchmark counts. The live Reader matcher is simpler. [Historical pairing results](../ArchiveProcessor/segbench-results/corpus-pairs.md#L5), [bench matcher](../ArchiveProcessor/scripts/segbench/corpus_pairs.py#L231)
3. Have the owner review a pilot and any optional unmarked-photo classifier pass, with time and cost up front. Write only to a separate derived archive, using the eventual canonical facts contract and approved preservation layout. Verify portable source associations, comparable browsing/search, key tag and date facets, Reader-to-Notes links, repeatability, and recovery from interruption. Keep a manifest and review log so a bad adoption can be discarded and rerun from untouched originals. The owner's storage and preservation answers still determine output format. Scratch implementation and real-corpus execution are later work. [Storage options and adoption](../execution-plans/storage-simplify.md#L420), [preservation options](../execution-plans/preservation-copies.md)

## Decision and queue

Can we put colour-to-type conversion, named-tree/JPEG pairing, and old-label backfill in one scratch-first adoption tool, then retire those legacy paths from the apps? The proposed split keeps trusted OCR reuse and ordinary capture, labels, folder maps, date rules and source links. The alternative is to keep a neutral, reusable backfill workflow for other archives and still put the owner's defaults and pairing rules in adoption.

**Owner choice, 2026-11-21 (call 31).** Use the single scratch-first adoption tool. Keep the optional
classifier with its time and cost preview in that tool. Plan a separate LLM-assisted migration kit for other
users' personal repositories behind W46.nice-to-have.
