## What the runs found, and the fixes made in the same item

1. **Run 1** (`StackedLayoutUITests` + the stacked light layout sweep): in the VM's 612 pt window the stacked note
   pane got 313 pt and its editor **9 pt**; the list kept its full remembered height and the window did not grow.
   The divider reading order did not find the table (the test looked for the wrong identifier).
   Fix: the panes' height is measured; the list is drawn, and its divider clamps, within what leaves the note its
   floor, never below 140 pt; the stacked minimum height is the two floors.
2. **Run 2**: the window now grows to the stacked minimum (612 → 639 pt), but an extract's editor got 103 pt
   against 110 pt for its details at a 440 pt note floor. Floor raised to 480 pt (minimum 627 pt; window 679 pt).
   The stacked audit found two issues the side-by-side audit never reached, because the narrower side-by-side list
   keeps those columns off screen: the Quality cell's unnamed hosting group, and the filter bar's decorative date
   dash measured as 1.25:1 text. Fixed: the group is labelled Quality; the dash is hidden from accessibility.
3. **Run 3** (the stacked tests and every `LayoutGuardUITests` and `AccessibilityAuditUITests` test): all
   side-by-side audits and sweeps pass; the divider drag, clamp and relaunch pass (list 330 pt at the bottom of
   the drag in an 869 pt window); reading order is table, divider, editor; Tab reaches the editor from the list in
   18 presses stacked and 22 side by side. Left: an extract's empty Tags cell had no description (empty Tags and
   Sources cells now read "No tags" / "No sources"), and the narrow-and-tall sweep could not grow a window that
   reached past the screen bottom (it now moves the window up first).
4. **Run 4**: the stacked audits light and dark, the stacked sweeps (narrow and tall 767×679 → 767×878), the switch
   test and `WritingJourneyStackedUITests` (all 7 journey tests stacked): **12 of 12 passed**.

The switch test: four switches, each with a line typed inside the autosave delay just before it. The text stayed in
the editor and reached disk each time, and the row stayed selected. The editor's scroll bar stayed near the end:
run 4 measured 1.0 → 0.91, 1.0 → 0.93, 1.0 → 0.90, 1.0 → 0.99 (the text reflows to the new width). The Extracts
window followed both switches with its extract still open.

5. **Stacked visual tours** (`VISUAL_REVIEW=1`): at the window's minimum the list's filter bar (three rows when
   narrow) spilled up under the toolbar over its Clear button at a 140 pt list; the UITest status probes showed

6. **Run 6** (checkpoint 9; the stacked tests, sweeps, audits and the stacked journey, 14 tests): 13 passed, no

7. **Run 7** (checkpoint 10; `StackedLayoutUITests`): 3 of 3 passed. The editor's scroll held at 1.0 → 1.0 on all
   four switches (`EditorScrollView` restores the caret, or the first visible line, after a resize). The divider drag
   ended at 306 pt in an 845 pt window; reading order table, divider, editor; Tab 18 presses stacked, 22 side by side.
8. **Tier-2 review of the whole item** (a subagent read the diff end to end): the layout, clamps, View menu and
   accessibility sound; no layout loop; one confirmed defect, fixed at checkpoint 11: the resize restore anchored to
   the start of the TextKit 2 layout fragment, which is the paragraph, so a reader in a long paragraph jumped to its
   first line; it now anchors to the visible line. Noted, not changed: the stacked minimum (about 760 pt with the
   toolbar) may not fit a 768 pt display with the Dock; both windows share one list height.
9. **Run 8** (checkpoint 10; the stacked tours light and dark): both failed, five surfaces unreachable (Note ▸
   Auto-fill, the row menu's Delete…, the Insert Link and Append to Extract alerts, the chip preview popover). The
   shots: the stacked list shows four or five rows, and XCUITest does not scroll a row into view before clicking, so a
   click on a row past the bottom or under the header sorted the list or selected nothing, and the next steps ran on
   the wrong note. Test fix at checkpoint 11: `revealRow` scrolls the list first; the default list height 240 → 300 pt
   (about seven rows in a 900 pt window). The side-by-side tours never needed it.
10. **Run 9** (checkpoint 11; the stacked tours): dark passed, "missing: none". Light **crashed the app** on the
    folder tree's second toggle at the typical size (1442×902): `_NSViewLayout` → `_crashOnException`, the exception
    thrown in `-[NSWindow _postWindowNeedsUpdateConstraints]` from `NSHostingView.invalidateSafeAreaInsets` nine
    superviews deep — a table cell. The Quality column's cells are `NSHostingView`s, on screen only in the stacked
    layout's wide list, and the tree's animation relaid the table while a cell's safe-area observer asked the window
    for a constraint pass. Fix at checkpoint 12: the cell's hosting view has no safe-area regions and no sizing
    options (the column sizes it; the rows are fixed height). The stacked order test now runs in a 1440 pt window with
    the column on screen and toggles the tree eight times, half of them mid-animation.
11. **Run 10** (the hosting-view change alone): the stacked order test passed with the Quality column on screen and
    eight tree toggles; the dark tour passed; the light tour **crashed again**, this time on the first toggle, with a
    different path to the same exception: `NSScrollView.layout` → the clip view's autoresizing constraints →
    `_NSConstraintBasedLayoutHostingView constraintsDidChangeInEngine` → SwiftUI's `AppKitPlatformViewHost`
    invalidating its layout → the root hosting view asking the window for constraints mid-layout. So the hosting
    view was a symptom. The cause is a loop: `StackedPanesLayout.sizeThatFits` measured its subviews, and the list
    holds the AppKit table, whose fitting size comes from the Auto Layout engine over its cells and changes while
    the table relays out; each constraint change invalidated the layout, which measured and placed the table again,
    until AppKit threw. The tour hit it because it toggles the tree right after the list reloads from Templates to
    All Notes, in a wide window, with the tree's animation running. Fix at checkpoint 12: the stacked layout never
    measures its panes (width from the proposal, floored at the list's 540 pt; height from the stored list height
    and the note's floor), and `NotesTableView.sizeThatFits` returns the proposal, so no layout can size the table
    from the engine. A new UITest repeats the tour's sequence three times (`testStackedTreeToggleSurvivesAListReload`).
12. **Run 11** (the layout and table size fixes): the four stacked tests passed (including the new reload-toggle
    test); the dark tour passed; the light tour crashed a third time, same exception, on the second toggle. Light
    had now crashed 3 of 3 after dark passed 3 of 3 in the same run, with pixel-identical shots.
13. **Runs 12 and 13** (a DEBUG `LayoutLoopProbe` in `packages/UITestSupport/App`, fed by the list's and the
    editor's scroll views): the **dark** tour crashed in both, on the first toggle, and run 12's light tour crashed
    at a folder click (Inbox) with no toggle at all. So the order was chance, the toggle is only one trigger, and
    the common ground is the list reloading in the wide stacked window. Run 13's dumps (threshold 12 calls in one
    run-loop turn) show only launches and two animation frames, no loop in those two scroll views; the dump of the
    crashing turn was lost because XCTest's "application is not running" failure unwinds past Swift `defer`, so the
    crashed test never collected it (nor restored the fixture, which is why run 13's light tour then found no
    sidebar rows: the tree was still hidden). Run 13 also left a JetsamEvent report for the system's
    AutomationModeUI, not ours. The dump now lives beside the store and is collected in `setUp` as well.
14. **Run 14** (the same code, the dump beside the store): both stacked tours **passed**, "missing: none", no crash
    report. Nothing in the app changed between runs 13 and 14, so the crash is intermittent: 5 of the 10 stacked
    tours since checkpoint 11 crashed, 0 of 2 here. Run 14's dumps hold only launches and the tree toggle's
    animation frames (two frames per turn, the list and the editor each tiled once per frame), no loop. The
    crashing turn was still uncaptured.
15. **Run 15** (the dump beside the store, fetched from the guest with `tart exec` because the crashed test collects
    nothing): dark passed; light **crashed** on the tree toggle after Templates → All Notes at 1442×902, and the
    probe had the turn (`W48-run15-layoutloop.txt` beside this file): the list's scroll view tiled in a two-state
    ping-pong, clip 1219 ↔ 1202 wide, document 1202 ↔ 1203, horizontal scroller shown ↔ hidden, last column
    550 ↔ 551, the vertical scroller flipping with it (the table 130 pt of rows in a 143 pt clip, the VM's legacy
    scrollers 17 pt). The tree's animation hands the stacked layout a fractional width; the table fits its columns
    to the fractional clip and comes out a point too wide; that shows the horizontal scroller, whose height makes
    the rows overflow and shows the vertical one, whose width changes the clip, and each tile's frame change wakes
    SwiftUI's host, which asks the window for another pass. Side by side the table is tall, so the rows never sit
    within a scroller's height of the clip, and no pass flips. Fix (checkpoint 13): `StackedPanesLayout` places its
    panes at whole points, and `NotesTableView.sizeThatFits` answers in whole points.
16. **Run 16** (whole-point placement and table sizing): dark passed; light **crashed at the same step**, and its dump
    (`W48-run16-layoutloop.txt`) shows the same two-state ping-pong with every width now a whole point: clip 1218 ↔
    1201 (the vertical scroller's 17 pt), horizontal scroller shown ↔ hidden, last column 551 ↔ 552, document 1201
    throughout. So the fractional width was not the cause; the scrollers' mutual dependence is (the horizontal
    scroller's height decides the vertical one, whose width decides the columns' fit), and what makes it fatal is
    SwiftUI re-laying the table between AppKit's tiles, so AppKit's own tile never gets to settle it. Whole-point
    placement is kept (harmless, and it removes one variable). **Open at the end of session 2**; the state and the
    candidate fixes were (a) overlay scrollers for the list, (b) `autohidesScrollers = false`, (c) a constraint-free
    table subtree; (b) was taken at checkpoint 14 (run 17).
17. **Run 17** (checkpoint 14, session 3: the list's scroll view no longer autohides its scrollers, so with legacy
    scrollers both tracks are always there and the clip depends on the frame alone): the two stacked tours and the
    four `StackedLayoutUITests`, three iterations (`TEST_ITERATIONS=3`): **18 of 18 passed**, 4,704 s, no new crash
    report, no build warning. Before the fix 6 of the 12 stacked tours since checkpoint 11 crashed; here 0 of 6.
    Overlay scrollers (the trackpad default) take no space, so they never had the loop and nothing changes for them;
    with "Show scroll bars: Always" the list now shows an empty horizontal track when the columns fit.
18. **Runs 18–20** (the whole suite at checkpoint 14; runs 19 and 20 were cut off when their sessions ended): run 18
    finished with 4 failures of 107, each passing alone: the two stacked `LayoutGuardUITests` and
    `testUndersizedSavedWindowWithWidePanes` (window drags that did not take) and `TransientStateUITests` (two
    recorder edge cases in 18 runs, the same at the commit before this item). Run 20's log showed the layout guards'

    the note window stayed 759 pt; alone, Extracts restored offset at (510,191) and the drag took. Fix (checkpoint 16):
    the sweep closes Extracts first.
