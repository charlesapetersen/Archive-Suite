## What was asked

Four `ArchiveNotes/KNOWN_ISSUES.md` follow-up entries (W7-S1a, S2, S3, S4, July 2026) listed live checks that were
never run because GUI work was paused and Notes had no scratch-store launch override. The checks were first mapped
to the existing UITests; the ones no test drove were written as `NotesW7ChecksUITests` and run in the VM (run 3);
the cited existing tests were then run on the same tree for this record (run 4), so no claim here rests on a
suite result from another day. An adversarial review of the new tests (a Fable subagent, read-only) found places
where a test could pass with the behaviour broken; the tests were strengthened and run again (run 5). Both the
first and the final results are kept below.

## The review, and what it changed

The reviewer's holes, each closed in the tests before run 5:

1. The scroll test put the cited block at the very end, so "scrolled past 0.8" could not tell the block from the
   end of the document. Now the block sits between 100 and 100 filler paragraphs and the test asserts a scroll
   position in 0.3…0.7.
2. The image-reload test counted attachments, and the Missing placeholder is also an attachment. Now it reads the
   `inlineImages` probe and asserts the asset's own bytes drew (no placeholder) right after the paste, after the
   reselect and after the relaunch.
3. The type-then-switch test could not say whether the idle autosave had already written the file when the switch
   happened. Now it reads the file just before the switch and logs the answer as an XCTest activity
   (`W7-S1a switch: A's file already held the edit before the switch = <bool>`); the result is reported below.
4. Create Extract and Append did not assert the source note untouched; now both compare the source's Markdown
   before and after. The two-block extract did not assert block order; now `#block-0` must precede `#block-1`.
5. The stale-ordinal test did not assert the "top of the note" half; now the source has 200 paragraphs and the
   scroll position must be at most 0.05 after the stale jump. The jump loads the note fresh, which also starts at
   the top, so this guards against a wrong scroll rather than isolating the stale-ordinal branch's own reset.
6. The Both-does-not-leak check read the Extracts window once; now it waits 2 s first. The "each window features its
   kind" claim rested on the harness's launch-argument pins; now the test also relaunches without the pins and
   asserts the Note window comes back on Both and the Extracts window on its own kind (the remembered choice,
   N-07's "persists").
7. The coverage map's "the clicks on the chip are the one gesture no test drives" was wrong (the image paste, the
   copy/paste pair and the selection placement are seams too); corrected above.

## Result — run 6, the header check alone: the jump lands short

`ONLY_TESTING=ArchiveNotesUITests/NotesW7ChecksUITests/testS3_JumpFromTheExtractsWindowScrollsToALowerBlock`,
2026-11-04 04:41: **failed**, `the cited block's header should be visible in the Note window after the jump — header
y 3698.2225274725274, visible 3718.0…3891.0`. The view stopped 20 pt below the header's top. In run 5 it stopped
several paragraphs above it. Either way the jump does not bring the block's header into view, though it scrolls to the
block's whole range (`NotePassageResolve.scrollRange` returns the block's range, header included, and the block is
shorter than the view). The likely cause is that `scrollRangeToVisible` runs straight after the new body is applied
(`MarkdownEditorView.updateNSView`, the W7-S3 scroll), while TextKit 2 still has estimated heights for the fragments
below the view. That is a reading of the code, not a measurement. Filed as `W40.fix-notes-jump-scroll-short`.
