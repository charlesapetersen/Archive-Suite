# W49.notes-lines-after-html — Returns after raw HTML are kept

## What was lost before the change

Probed in the unit bundle (`MarkdownBridge.parse`, typed Returns, `MarkdownBridge.serialize`):

| Typed | Editor text | Saved | Reopened as |
|---|---|---|---|
| 1–3 Returns after `<div>\nx\n</div>` | `</div>` + n newlines | `<div>\nx\n</div>` | no newline |
| 2 Returns after `a <b>x</b>` | `</b>\n\n` | `a <b>x</b>` | no newline |
| file `<div>\nx\n</div>\n\nafter` | | | `</div>\n\nafter`: the blank line that ends the block shown as an empty line, so one typed Return came back as two |

## The forms, and why they read back

- **After an HTML block:** the separator the Styler puts after it is one newline, as after other blocks (it was two
  before plain text). n Returns are written `\n\n` (the blank line that ends the block, read back as that one newline),
  then a `\` line for each one more, then `&nbsp;` at the end of the note or before a block or chip. Before text, the
  `&nbsp;` is not needed. In a quote the same lines are quoted (`> <div>x</div>`, `>`, `> &nbsp;`).
- **Read back, an `&nbsp;` paragraph after an HTML block** leaves only its separator beside the block's, both at the end
  of the run; their newlines past the first are written as those empty lines again (plain text and quotes).
- **After HTML inside a paragraph:** `a <b>x</b>\` then `&nbsp;` reads back as `a <b>x</b>\n`, so the ordinary form
  is used. The new `.noteBlockHTML` attribute (Apple's `.blockHTML`) tells the two apart.
- **An HTML block a blank line does not end** (an unclosed `<!--`, `<pre>`, `<script>`, `<?`, `<![CDATA[`, a headerless
  chip's opener) keeps the old behaviour: Returns dropped, as everything after it is its text.

Measured: Apple gives adjacent HTML blocks as one run with no presentation intent and without the blank lines between
them (`<div>a</div>\n\n<div>b</div>` arrives as `<div>a</div>\n<div>b</div>\n`; `<div>a</div>\n\n<!-- open\nx` as
`<div>a</div>\n<!-- open\nx\n`). So the open check reads every line of the run: one that opens a block of those kinds
with no end after it counts as open. A `<div>` block holding such a line is therefore treated as open too; queued as
`W49.notes-html-block-starts` (behind nice-to-have). A file's two adjacent HTML blocks also save as one (the blank line
between them was already dropped before this item); the rendered HTML is the same.

## Tier-2 review

Opus read the code only and traced the cases. It found:
- (1) `.noteBlockHTML` leaked into typed text through the typing attributes, so a second Return typed in text below an
  HTML block came back as an empty line more. `EditorTextView.typingAttributes` now strips it.
- (2) A quoted HTML block lost the empty line above a following block or chip on the second save. The quote branch now
  counts the stacked separator as the plain branch does.
- (3) After an unclosed HTML block a Return wrote `&nbsp;` into the block, shown as text. The open check above restores
  the old drop there.

All three have tests (`linesAfterAnHTMLBlockFromTheReview`). A re-review of the fixes found no new break; the open check
errs only toward open (Returns dropped, nothing written). `<?>`, `<!-->` and a `<pre>` closed by `</script>` were then
made closed, as CommonMark reads them.
