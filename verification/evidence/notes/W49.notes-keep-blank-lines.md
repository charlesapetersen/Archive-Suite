# W49.notes-keep-blank-lines — the editor keeps the blank lines and empty list items typed

2026-11-19, unattended. Owner call 20 (2026-11-19): keep what I type. Unit bundle on the host (app-hosted, draws
nothing), UI tests in the Tart VM (`ops/gui/vm-gui-runner.sh notes xcuitest`), the scratch fixture store only.

## What was lost, measured on main before the change

Typed through the real `EditorTextView`, then `MarkdownBridge.serialize`:

| Case | Editor text | Saved | Reopened as |
|---|---|---|---|
| 1. two Returns after `A`, before `# T` | `A\n\n\nT` | `A\n\n# T` | `A\nT` |
| 2. Return after `a` in `- a` / `- b` | `a\n\nb` | `- a\n- \n- b` | `a\nb` (Apple's parser drops `- ` alone) |
| 3. Bulleted List on the empty last line after `A` | `A\n\n` + list typing attributes | `A` | `A` |
| 4. file `# H\n\n\n\nText` | `H\nText` | — | — |

## Which forms read back, checked with `AttributedString(markdown:)` and the Styler

- `&nbsp;` alone on a line reads as a U+00A0 paragraph of its block (plain, or a list item in `- &nbsp;`), with the
  Styler's separators around it. A bare `-` line is dropped by the parser (the next item's ordinal skips one), and
  `- \` reads as a literal backslash, so `- &nbsp;` is the empty-item form.
- Hard breaks before `&nbsp;` (`A\` newline `&nbsp;`) read as `A`, newline, U+00A0, so k empty lines before a block
  are k hard breaks ending in the `&nbsp;` line.
- The parser's source positions (`appliesSourcePositionAttributes`) give each block's lines: a fenced code block spans
  its fences, a soft break has none. So the blank lines between two blocks are counted from them.

No case needed another form, so nothing was asked of the owner.

## The change

- `MarkdownBridge.restoreEmptyLines` deletes a U+00A0 that is alone on its line (not in code, inline code or raw
  HTML, not before a chip). An empty item at the very end leaves its kind on the newline before it
  (`.noteNextLineKind`).
- The serializer writes the empty lines after text before the next block as hard breaks ending in `&nbsp;`, a
  paragraph with no text as `&nbsp;`, an empty list item as `- &nbsp;`, and an empty item kept on the last line.
  `collectParagraphs` keeps a list item that is a newline alone.
- `MarkdownStyler.extraBlankLines` adds one empty line per blank line past the first between two blocks of a file
  (not in a list, between two quotes or beside raw HTML). Source positions are asked for only when the text has two
  blank lines in a row.
- A list toggled on the empty last line, or the empty item Return makes there, is kept on the newline before it
  (`EditorFormatting.keepEmptyLastLineKind`); the typing attributes and `ListMarkers.trailingMarker` read it.
- A typed entity reference (`&nbsp;`, `&amp;`) is escaped `\&`, so it reopens as typed and never as the marker.
- After an inline image's line, the blank line was written twice (the join and both separator newlines); that
  showed once the reader honoured blank lines, and is written once now.

## Tier-2 review

An Opus adversarial review of the diff (code read only, nothing run) found:

- **Where nothing follows, a stray U+00A0** (HIGH): the marker was written for an empty line at the end of a
  segment when a one-newline separator ended it (Return above a chip; a block below deleted). The reader kept that
  U+00A0 before a chip or at the end, as text. Now the writer writes the marker only when a block follows in the same
  text, and the reader deletes a lone U+00A0 line there too.
- **An empty item above a chip kept its U+00A0** (HIGH): the same reader rule, and the writer counts U+00A0 as an
  empty item's text.
- **A stale kept kind** (LOW–MEDIUM): `.noteNextLineKind` stayed on the newline after text was typed after it, so
  deleting that text brought the list back. `EditorTextView.shouldChangeText`/`didChangeText` now clear it when
  text is inserted on that line.
- **Lines with no run counted as blank** (LOW): a link reference definition's lines. Every line between the two
  blocks must now be blank in the source.
- Not changed: a plain paragraph cut in two by a nil block kind next to `.plain` (LOW, suspect); the editor gives
  typed text a kind, and the old output lost that line too.

Each fix has a test: `noStrayMarkerWhereNothingFollows`, `theKeptKindGoesOnceTheLineHasText`,
`linesWithoutARunAreNotBlankLines` (a rule turned out to be a run of its own, ⸻, so it is not in the test).
