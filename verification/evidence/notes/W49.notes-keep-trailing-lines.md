# W49.notes-keep-trailing-lines — Returns at the end of a note and above a chip are kept

2026-11-19, unattended. Owner call 20 (2026-11-19): keep what I type. Unit bundle on the host (app-hosted, draws
nothing), UI tests in the Tart VM (`ops/gui/vm-gui-runner.sh notes xcuitest`), the scratch fixture store only.

## What was lost before the change

Typed through the real `EditorTextView`, then `MarkdownBridge.serialize` (the old unit tests recorded it):

| Case | Editor text | Saved | Reopened as |
|---|---|---|---|
| Return after `A` at the end | `A\n` | `A` | `A` |
| Two Returns after `A` above a chip | `A\n\n` + chip | `A` + header | `A\n` + chip |
| Two Returns after `> q` at the end | `q\n\n` | `> q` | `q` |
| Two Returns after text below a chip's thumbnail line | `￼\n\nText\n\n` | `![d](t)\n\nText` | `￼\n\nText` |

## The forms, and why they read back

- **At the end of the note:** every newline after the last text is a `\` line break, and the last line is `&nbsp;`
  (`A\` then `&nbsp;`). Apple's parser reads that as `A`, the newlines, then U+00A0. `restoreEmptyLines` deletes the
  U+00A0 because nothing follows it, and the newlines stay. A separator left at the end by a deleted block counts
  as newlines too.
- **Above a chip:** the last block of the segment counts as followed, as it would before another block. The newline
  that `endLine` adds before every chip on reopen comes after the `&nbsp;` line, and it is the boundary, which is
  how `plainLines` already counted it.
- **A quote:** its empty last lines are written as `> q\` then `> &nbsp;`. `restoreEmptyLines` now accepts quote
  lines too.
- **A copied passage** (`NotePassageSource.snapshotMarkdown`): trailing newlines and spaces are trimmed from the
  selection, but not those of a code block, inline code or raw HTML, so the passage gains no marker.
- **Still dropped, queued as `W49.notes-lines-after-html`:** Returns after text that ends in raw HTML. They were
  dropped before this item too.

## Tier-2 review

Opus read the code only and traced the cases. It found:
- (1) Returns after text below an image line (a chip's text opens with its thumbnail) were still dropped, because
  the image's separator comes back as `leading`.
- (2) A passage selection ending in spaces gained an empty line.
- (3) A passage lost a code block's empty last line.

All three are fixed, with tests (`returnsAfterTextBelowAnImageAreKept`, and
`testSnapshotMarkdown_trailingNewlinesOfTheSelection_areNotEmptyLines`).

The review also traced these, and they hold:
- A note that is only newlines.
- A separator left after a deleted block.
- A chip with an empty body.
- Older files: `A\n` and `A\n\n\n\n` are unchanged. `A\n\n&nbsp;` is rewritten once, then stays stable.
- The chip header still begins a line.
