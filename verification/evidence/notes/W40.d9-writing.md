## How the typing is done

Every keystroke goes through `typeText` into the styled editor's own text view (`an.editor.text`), after clicking
it until it reports keyboard focus and moving the caret to the end with ⌘↓. It took focus on the first click in
every run. The bundle's other editor tests type through the `an.editor.test.*` seams, on the belief (comments in
`NotesGUITests.swift`) that XCUITest cannot make the styled text view first responder; in this lane that belief
does not hold for typing. The one seam used here is `an.editor.test.pasteImage`, for the forced asset failure,
because that check is about the failed write and not about ⌘V.

### Finding 1 — a typed Return does not survive a reopen (`W40.fix-notes-return-paragraph`, S2)

Two paragraphs typed after the fixture's last line, each started with Return, are saved one newline apart:

```
# Plain Note

A plain note with **bold** text and no source blocks.
Typed by hand in the W40.d9 journey.
Quit straight after typing this.
```

Markdown reads consecutive lines as one paragraph, and so does the app. After the relaunch the styled editor
shows them as one:

```
[d9] step 3 relaunched editor text: "Plain Note\n\nA plain note with bold text and no source blocks. Typed by hand
in the W40.d9 journey. Quit straight after typing this."
```

So every paragraph break a user types in the styled editor is lost the next time the note is opened. No text is
lost. Likely cause [I, not checked]: `MarkdownBridge.serializeBodySegment` (`Editor/MarkdownBridge.swift:413-443`)
splits paragraphs by runs of the `.noteBlockKind` attribute (`collectParagraphs`, `:453`). A typed paragraph
inherits `.plain` from the one before it, so both form one run and the Return inside it is written as a bare
newline.

### Finding 2 — an edit made outside the app is overwritten without a word (`W40.fix-notes-outside-edit-overwrite`, S1)

With the note open, the test appended a paragraph to the `.md` in place, the way another editor would. The app has
no file watcher, so the editor kept its copy. The next keystroke's autosave wrote that copy back:

```
[d9] outside edit: editor reloaded it within 3 s = false
[d9] outside edit after the app's save: on disk = false; status line = none; alerts = 0, sheets = 0
[d9] body after the save:
# Plain Note

A plain note with **bold** text and no source blocks.
Typed after the outside edit.
```

`NotesModel.setBody` (`Core/NotesModel.swift:1121`) re-reads the item through `NoteStore.withItem` but then replaces
its blocks and body text wholesale with the editor's markdown, so front-matter edits made outside would survive and
body edits do not. Reproduced in 6 of 6 runs (three VM runs). S1: text the user wrote is deleted from disk.

### Finding 3 — a failed image write is not shown (`W40.fix-notes-asset-write-silent`, S3)

The test made the note's `assets/` folder read-only (`chmod 0555`, restored after) and pasted a PNG:

```
[d9] forced asset failure: paste outcome = ok store=11111111 sel=11111111
[d9] forced asset failure: asset files landed = 0; status line = none; alerts = 0, sheets = 0
```

The note keeps a reference to a file that was never written. `ItemAssetStore.addAsset`
(`Editor/InlineImageAttachment.swift:355`) only `NSLog`s the failure. `ArchiveNotes/KNOWN_ISSUES.md` records this
as a residual ("logged, not surfaced to the user"). This run confirms it in the real app. S3: the image is lost but
can be pasted again, if the user notices.
