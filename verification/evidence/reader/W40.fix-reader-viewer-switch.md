# W40.fix-reader-viewer-switch — moving between open files, measured

2026-11-11. The owner's point 5 (Reader notes of 2026-11-10): moving between open files in the document window was slow.
W40.reader-scale-measure's lane put a switch at 245 ms main-busy at -O, 188 ms of it the panes' page copy and draw,
emulated by drawing the page on the main actor. This item measured what a real view does first.

## 1. Where a switch's time goes (host probe, -O, 5 real sample PDFs, read only)

| step | time |
|---|---|
| `PDFDocument(url:)` | 0.8–2.2 ms (65 ms the first, cold) |
| `page.copy()` | 0.0 ms |
| first draw of the page at 900×1200 | 147–177 ms |
| a copy's draw after the page was drawn at that size | 1.3–7 ms |
| a draw at another size after a warm draw | 136–165 ms (as cold) |
| JPEG original: `NSImage(contentsOf:)` + `PDFPage(image:)` | 16–17 ms (119 ms the first) |
| JPEG first draw at 900×1200 / 1800×2400 | 20–38 / 47–51 ms |

`page.copy()` does not decode, and a copy shares its page's decoded image. Core Graphics keeps it at one resolution only,
and a warm draw on a background queue behaves the same, so warming a document cannot serve PDFView's tiles. The
item's premise that the copy forces a full decode was wrong; the copy stays.

## 2. Real PDFViews in the VM: where the main thread goes (sample, 30 s, about 15 switches per phase)

`ViewerSwitchUITests` on the W40.c2 sample (`READER_JOURNEY=rehearsal`), Debug, macOS 27.2 guest; `sample` in the guest.

| main thread, samples | prefetch on | prefetch off (the viewer before) |
|---|---|---|
| total / idle | 17,483 / 10,079 | 17,359 / 10,593 |
| XCUITest's accessibility snapshots | 4,719 | 4,218 |
| PDFKit (all frames) | 65 | 113 |
| image decoding (ImageIO) | 1 | 1 |
| `loadCurrent` / a pane's `makeNSView` | 12 / 16 | 9 / 20 |
| **`PDFKit.PDFTilePool.workQueue`** (another thread) | 1,778 | 1,879 |

PDFKit draws a page's tiles on its own serial queue. The decode never was main-thread time; it was the wait for the
first pixels, 150–500 ms, with the page blank. The lane's 188 ms drew the page on the main actor, which no real view
does. The app's own switch work on the main thread is a few ms.

## 3. 200 switches, 5 open, real PDFViews (VM probe, Debug)

`ViewerSwitchProbe` (DEBUG, `-ARSwitchProbe`): main-busy from a run-loop observer over the 1.2 s after each switch,
footprint every 20 switches. Two runs each.

| | prefetch on | prefetch off |
|---|---|---|
| footprint growth over 200 switches | +29 MiB, +9 MiB | +2 MiB, −7 MiB |
| image page already drawn at the switch | 200 / 200, 200 / 200 | 0 |
| main-busy median (harness included) | 94.5, 95.5 ms | 90.8, 91.2 ms |

Memory stays flat with a fresh PDFView per page: no IOSurface growth over 200 rebuilds with 5 open, so the views
are not kept and swapped (DV-3's text-selection wedge stays avoided; a pane's `makeNSView` is about 2 ms). The
+9 to +29 MiB is the window's four bitmaps (pane-sized, about 4–10 MB each). Main-busy in the VM is dominated by
the test's own accessibility queries (§2), the same in both runs; it is not a budget figure.

## What changed

- Document window: the image page of the open file and the files either side is drawn ahead to a pane-sized bitmap
  (`PreviewImagePrefetcher`, one per window, 4 kept), and shown by the preview's `PlaceholderPageOverlay` until
  PDFKit's tiles land. The JPEG source has none (its first draw is 20–50 ms).
- `DocumentViewerModel`: the next and previous files, and their JPEG originals, are opened on a background queue and
  handed over finished (`NeighbourCache`); the file just left is kept; an entry is served only while its stat(2)
  stamp (size, mtime, inode) is unchanged; a dataless file is not opened ahead; an open no longer wanted when its turn
  comes is skipped.
- `JPEGPartnerIndex`: lookups by dictionary instead of scanning every candidate (with a filesystem prefix lookup each)
  per resolve; the viewer's two scans of `candidates` became `candidate(atPath:)`.
