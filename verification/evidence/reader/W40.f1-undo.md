## What was tested

The path ⌘Z takes: `NavigationModel.mark(.read)` on a selection, then `NavigationModel.undoLast()`
(`Views/NavigationModel.swift:1064-1113`), with the file's tags read back from disk through a fresh `URL`.

## Result — 4 tests green, 3 of them holding an expected failure; three facts established

```
testTheUndoHistoryDoesNotSurviveARelaunch          passed
testAPartlyFailedUndoIsReportedAsComplete          passed  (XCTExpectFailure W40.fix-reader-undo-partial)
testUndoRefusesAFileSwappedUnderItsPath            passed  (XCTExpectFailure W40.fix-identity-url-cache)
testFileIdentityThroughAReusedURLSeesASwap         passed  (XCTExpectFailure W40.fix-identity-url-cache)
Executed 4 tests, with 0 failures (0 unexpected)
```

1. **Undo is memory-only (as suspected).** A mark made in one `NavigationModel` gives it `undoDepth == 1`. A second
   model on the same root and the same defaults domain (everything a relaunch reads back) has `undoDepth == 0`, and
   ⌘Z there changes nothing on disk and says nothing. There is no record of the change anywhere: the §12 audit
   ledger (`R-46`) does not exist.
2. **A partly failed undo is reported as complete (as suspected).** Two files marked Read as one step; one is then
   removed. `undoLast` restores the other, drops the failed entry (`try?`, `:1108`), leaves `undoDepth == 0` so it
   cannot be retried, and says `Undid 1 change.` with no word about the file it could not undo. `mark` in the same
   situation says `Marked 1; 1 could not update.`, as Safety §11 requires. Filed `W40.fix-reader-undo-partial`
   (S3).
3. **New: the §6 identity re-check does not see a file swapped under its path (S1).** The test first written for
   fact 2 swapped the file (removed it and wrote a different one at the same path, tagged `Read`), expecting §6 to
   refuse it. Instead the swapped file was re-tagged `Unread` and the status said `Undid 2 changes.` (first run,
   before the test was restructured; the assertion messages were "the swapped file was refused, not re-tagged:
   ["Unread"] is not equal to ["Read"]" and "Undid 2 changes. is not equal to Undid 1 change."). The writer-level
   test `TagWriterTests.testApplyWithMismatchedIdentityAbortsAndLeavesReplacementUntouched` passes only because it
   hands the writer a *new* `URL`. `testFileIdentityThroughAReusedURLSeesASwap` isolates the cause:
   `FileIdentity.capture` (`packages/ArchiveCore/Sources/ArchiveCore/Tags/TagWrite.swift:135`) reads
   `fileResourceIdentifier` through the `URL` it is given, and the same `URL` instance answers from its
   resource-value cache after the file is replaced, while a fresh `URL` sees the new file. The Reader passes the
   `ArchiveFile`'s own `url` both to `liveIdentity()` and to the write, so the check compares the cache with
   itself. Filed `W40.fix-identity-url-cache` (S1, a write to the wrong file).

## Not tested here

- Whether the edit-time paths (`mark`, the inline editor, ⌘I, rename) can hit the same cache. They capture the
  identity just before writing, so the window is short, but if discovery already cached `fileResourceIdentifier`
  on the `ArchiveFile.url`, the edit-time check compares against the discovery-time identity. The fix item checks
  this; Notes' `NoteStore` also calls `FileIdentity.capture`.
