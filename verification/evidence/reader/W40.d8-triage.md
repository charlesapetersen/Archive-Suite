## What is checked

After every step the test snapshots the whole root: each file's Finder-tag xattr decoded with its colour
suffixes (`Blue\n4`), every other xattr by SHA-256, and every file's size and content SHA-256. A step passes
only if exactly the files it names change, in exactly the named tags, and every other tag, colour, xattr and
content byte is unchanged. Files that a step does not name must stay byte-identical. Files are named by alias
(`f60`); the alias-to-path lines stay in the uncommitted logs.

Two reproduced defects are carried as non-strict `XCTExpectFailure`s naming their fix items, so the journey can
sit in the gate's lane without hiding anything else (every other check fails outright):
`W40.fix-reader-tag-quarantine` and `W40.fix-reader-inline-keys`.

Every Reader write (Mark Read, the inline editor, the ⌘I sheet) stamps the file it writes. A file that already

undo and merge wrote to files already stamped by earlier steps, so they show no new change. The content,
`com.apple.FinderInfo` and every other tag were untouched. Context: the W40.c2 sample's 8,750 files carry no
ArchiveReader stamp yet, but Preview has stamped 1,789, Photos 1,659 and PDFpen 74.

### Observation, not a defect — macOS rewrites the tag xattr's encoding on a written file

```
[d8]   f03 before [Read, Policy, 1924, Stanford, Trustees, Admissions, Academic Council, Blue\n4]
[d8]   f03 after  [Read\n0, Policy\n0, 1924\n0, Stanford\n0, Trustees\n0, Admissions\n0, Academic Council\n0, Blue\n4, W40d8 Group\n0]
```

Many corpus files store tags bare (`Read`). When the Reader writes such a file, every tag comes back with an
explicit no-colour suffix (`Read\n0`). Finder reads the two forms as the same tag with no colour, so nothing is
lost; the comparison treats them as equal and notes the rewrite. Colours survived on every written file
(`Blue\n4`, `Gray\n1`, `Red\n6`, `Purple\n3`).
