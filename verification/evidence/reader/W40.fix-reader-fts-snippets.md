# W40.fix-reader-fts-snippets — every search hit gets its snippet

2026-11-05 · checkpoints `W40.fix-reader-fts-snippets (checkpoint 1)` and `(checkpoint 2)`, then the completing
commit · builder's run, not the recheck (builder is not verifier).

**The problem** (owner, Reader guided session 1, 2026-11-04: "Search snippets is important"). `searchRanked` gives
snippets to the top 300 hits and stops after 250 ms (`W40.fix-reader-fts-snippet-stall`), so a slow query left hits
with no preview line, and every hit past the 300th never had one.

**What changed.**
- `ContentIndex.snippets(_:for:budget:)` makes the snippets for given hit paths, under the same 250 ms budget,
  and says how many it looked at. `NavigationModel.searchSnippet(for:)`, which each name cell calls as it is drawn,
  queues a hit that has none. One task at a time drains the queue in batches of 40, newest first so the rows on
  screen come before rows scrolled past, at most 400 waiting. The work runs in the index actor, off the main
  thread. After each batch the table reloads the visible rows that got a snippet (`takeFilledSnippetPaths`).
- A query made only of stop words (`the`, `of the`) keeps them in the snippet expression, and FTS5's `snippet()`
  cost grows with the square of their instances: the first run of this lane found one fill batch for `the` holding
  the index for **910.8 ms** on the sample, one long body. Such a query now reads the body and builds the fragment in
  Swift (`SearchSnippet.fragment`), stopping one window past the first match.

**Tests.** `ContentIndexTests.testSnippetsForPathsFillWhatTheSearchLeftOut` (paths with no body or no row count as
answered; out of time, nothing is). `SearchSnippetFillTests` (a model whose search gave no previews gets one for
each hit through the queue, and the table is told exactly which rows; the fragment's window and ellipses).
`ReaderAtSizeTests.testCommonWordPhraseSnippetsStayFastOnLongBodies` adds `of the` over 60 long bodies: 60 of 60
previews in 4.9 ms; with the scan route turned off for one run, 2 of 60 in 262 ms, **TEST FAILED**.

**At size.** `ops/scale/run-reader-at-size.sh --optimized` (both lanes), 2026-11-05, passed, the sample listed
unchanged (9,315 paths, listing SHA-256 `62801cd97755a85a`). The fill was run as the list runs it, over the first
1,000 hits in rank order (as if scrolled through) in batches of 40; "slowest" is the longest one call holds the
index actor. The test asserts every batch under 500 ms.

**The hits still without a line have no text to quote** [I]. The sample holds 74 JPEGs with `kennedy` in the
name and 104 with `president`; `Kennedy` has 70 hits without a preview on the sample. A JPEG's index row has a
name and no body. At 102k the sample is replicated about 18 times, and bm25 puts these name-only rows first (the
name weighs 10), so the first 1,000 `Kennedy` hits are photographs. Their name, which is what matched, is the row's
first line already.

**The 150k list.** `testListAtOneHundredFiftyThousandFiles` draws 200 screens of 35 rows × 9 columns with fresh
cells, then again with a query matching every row and no snippet yet, so every name cell queues its path: median
79.0 ms against 83.9 ms without a query (noise; the queue is a set lookup a row). 400 paths queued, the cap.

**Verdict.** Every hit with body text gets its line once its row is drawn, and no fill call held the index longer
than 37 ms on either tree. The list never waits for it: the search returns as before, and the fill runs in the
actor between other calls.
