# W40.fix-reader-docpanekeys-vm-harness — why DocumentPaneKeysUITests lost the image page (2026-11-27)

Guest: `archive-gui-runner`, macOS 27.2, Xcode 27.2, kept between calls (`VM_KEEP=1`). Base `261ca227`.

## What was wrong

It was the app, not the test and not a guest change. `W40.h2` read it as a guest change because the test also
failed at `d3f04308`, where it had passed on 2026-11-12. The test run showed the page lookup succeeding until the
first Zoom In on the image page. After that it failed for good.

A probe test printed the document window's accessibility snapshot around each zoom step:

| Step | "Original image page" found | Scroll views in the window | Window content group's children |
|---|---|---|---|
| opened, Reset Zoom, click on the image | yes | 3 | 7 |
| ⌘= once, ⌘= twice (image zoomed past fit) | no (4 s of polling) | 0 | **0** |
| ⌘0 Fit Page | yes | 3 | 7 |
| Document ▸ Zoom In (image) | no | 0 | 0 |
| click in the text pane, Zoom In (text) | yes | 3 | 7 |

The snapshot returned in 0.17 s, so this was not a timeout. With the image page zoomed, the window's whole content
(both panes, the thumbnails, the status bar) had no accessibility children: VoiceOver would have lost the document
too, not only XCUITest.

Each variant was launched with its own switch in a scratch build:

- `ReaderPDFView.namePages` switched off: the three scroll views stay through every zoom (the page untitled, as
  expected).
- The recursive walk kept and the title setter skipped: the content still empties when zoomed. So the walk, not the
  setter, is the cause. On macOS 27.2, asking PDFKit's descendants for their children *inside* our own
  `accessibilityChildren()` query, while zoomed, makes the whole content group report none.
- The title set only when it differs: still empties.
- The walk deferred to the next main-queue turn, after the query returns: the page is found and titled at every
  step, and the scroll views stay at 3.

## The fix

`ReaderPDFView.accessibilityChildren()` returns PDFKit's children untouched and queues one walk to title the AXPage
nodes, coalesced while a walk is pending. The setter now runs only when the title differs. A query that meets a page
PDFKit has just rebuilt sees it untitled once, and the next query sees the title. The test file is unchanged.

## Runs

- `DocumentPaneKeysUITests` (both tests), 3 of 3 runs green: 157.8 s, 156.6 s and 157.1 s for the class.
- In the same guest: `CopyTextPaneUITests`, `ImageContextMenuUITests`, `InvertImagesUITests` and
  `ViewerUITests/testDocumentViewerOpens` pass.
- `AccessibilityAuditUITests` (4) fail the same way with and without the fix. The light-mode test was run on the
  unchanged app as a baseline and gave the same three findings: preview-sheet thumbnail with no description,
  document-viewer Parent/Child mismatch, and "Not recorded" contrast at 3.95:1. These are already listed under
  `W49.ui-fails-under-coverage` (AccessibilityAudit ×4).
- Host: `PDFPaneAccessibilityTests` now lets the queued naming run before it reads the title. It gains a pass zoomed to
  3×. The Reader unit bundle passes (DeepLinkTests skipped, per the usual rule).
