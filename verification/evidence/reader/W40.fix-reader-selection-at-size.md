## What the fix is

- **The selection is found by the list's sort keys, not by a scan.** `displayedPositions(of:)` looks each selected row
  up in the library's row index and binary-searches `displayed` with `LibraryPresentation.listedBefore`. Rows with equal
  keys are walked through, and a row counts as found only on an exact path match. A miss falls back to the old scan, so
  the result is never wrong: a row the list does not show, a library row newer than the list, or a list sorted some
  other way. More than 4,096 selected rows also fall back, since one pass is then cheaper.
- **The cache follows the selection's changes.** While the list keeps its order (`displayedOrderGeneration`), the cache
  keeps the selection's positions and applies only what was added and removed, up to 64 rows per change. It reads every
  row from `displayed`, so a row replaced in place shows its new tags. It is in the list's order, relevance included.
  Before, under a relevance sort, it followed `LibrarySort` order.
- **`moveSelectionInList`, the prune and the preview prefetch** use the same positions.
- **The selection's UserDefaults write waits for a 0.3 s pause.** It is flushed at quit (`flushSelectionWrite`).
- **A hidden inspector is not built.** The library window's inspector edits `inspectorTarget`: the selection's paths,
  frozen while it is hidden. Its identity is a generation that changes only when the set of files does, not their
  order. `TagInspectorView` is `Equatable` (identity, visibility, model) and no longer observes the model. Its editor
  follows the model through an `InspectorFeed` only while shown, and re-follows if the model changes. A hidden
  inspector, in the library window or in each document window, therefore costs nothing per publish. A draft survives
  ⌘I while the selection is unchanged, as before.
- **The indexing count publishes on its own.** `IndexProgress` is observed only by the status bar's label. The model
  publishes `isIndexing` at a pass's start and end, so an indexing tick no longer re-runs the list window or the
  inspector. The selection stays on the navigation model: moving it off would rewrite every view's binding for no
  measured gain, since a selection change now costs under 1 ms in the model.

## Tests

- `SelectionAtSizeTests` (new, 8 tests):
  - the selected files are the listed rows, in list order, in either direction;
  - a row the list does not show is left out;
  - a randomized run of 300 selection changes and a re-sort is held to a scan of the list at every step;
  - the preview arrow steps from either end of a selection;
  - a hidden inspector holds its target and takes the selection when shown;
  - re-sorting the same files keeps the inspector's identity;
  - the selection is written once the changes pause;
  - an indexing tick does not republish the model.
- `NavigationModelTests` and `RestoreListPlaceTests` flush the debounced write before they read it back.
- The whole `ArchiveReaderTests` bundle passed: 742 tests, DeepLinkTests skipped as usual, no new warnings.
- An adversarial review (Opus) found nothing serious. Its one real point was fixed: the document window's feed
  re-subscribes when the library window's model changes. Its other notes are recorded above: the order change under
  relevance, and a draft surviving only while the selection is unchanged.
