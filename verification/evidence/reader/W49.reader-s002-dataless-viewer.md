# W49.reader-s002-reproduce — the Reader's viewer, preview and bitmap prefetch download a cloud placeholder

Suspect `S-002` (`verification/SUSPECTS.md`), 2026-11-20, Opus 5.5. Reproduced, and wider than the entry says: the
browser list downloads a placeholder when the row is **selected**, before anything is opened.

## The code still says what the suspect says (rule 5a(1))

| Path | When it runs | Guard |
|---|---|---|
| `DocumentViewerModel.loadDocument` (`Views/DocumentViewerModel.swift:952`) — the document window and `PreviewSheet` | the user opens the file (Return, Space) | none: bare `PDFDocument(url:)` |
| `PreviewImagePrefetcher.prefetch(paths:)` → `render` (`Views/PreviewImagePrefetcher.swift:99`, `:155`) | **every list selection change** (`PreviewImagePrefetchModifier`, preview shown or not), the rows either side while the preview is up, and the document window's `neighbourhoodPaths` (index ±1) | none: `FileStamp` reads `SF_DATALESS` but nothing checks it |
| `DocumentViewerModel.openDocument` (neighbour prefetch) | the files either side of the one opened | **holds**: `NeighbourCache.start` returns nil for a dataless file ("that would download it unasked") |
| `DocumentViewerModel.performFind` (`:719`) | Find in a multi-file selection | none (user-started; opens every file in the selection) |
| JPEG partner, link thumbnail, header fields, folder dating, Improve OCR | — | hold (dataless checks or the thread guard) |

The neighbour guard's own comment says opening ahead must not download unasked, so the prefetcher's download is not
deliberate (rule 5a(3)). Whether an **explicit open** may download is a question for the owner (Daemon Report).

## The placeholder

As in `W49.notes-s007-reproduce`: the owner's OneDrive (`~/Library/CloudStorage/OneDrive-Stanford`) holds dataless
PDFs; the same non-sensitive 6.2 MB file was used (`Personal/Outdoors/Epicurean-Backpacker-JJF-082515.pdf`,
`compressed,dataless`). Nothing in the corpus was touched. Both probes set the process materialization policy back
to on first: the engine starts sessions with it off, and a Reader started from Finder has it on.

## Run 1 — the shipped prefetcher (`W49.reader-s002-prefetch-probe.swift`)

Compiles the shipped `PreviewImagePrefetcher.swift` (with a stand-in `NavigationModel`, which only its SwiftUI
modifier names) and makes the call a selection change makes, `PreviewImagePrefetcher.shared.prefetch(paths:)`:

```
set process ON: 0
before: dataless=true stamp.isDataless=true
bitmap=940x1216 secs=1.58
after: dataless=false
evicted
```

Selecting the row is enough: the whole file came down to draw the bitmap, though its own `FileStamp` had just said
it was dataless.

## Run 2 — the viewer's calls (`W49.reader-s002-probe.swift`)

The same calls as `loadDocument` (viewer/preview), `openDocument` (the neighbour open, run without its cache
guard) and `render`, bare, against a control inside the thread guard `CorpusWalker.withDatalessMaterializationDisabled` sets:

```
mode=guarded   pages=-1 secs=0.01  after: dataless=true
mode=viewer    pages=54 secs=2.48  after: dataless=false  evicted
mode=neighbour pages=54 secs=1.72  after: dataless=false  evicted
mode=prefetch  pages=54 secs=1.22  after: dataless=false  evicted
```

The file was evicted after every download and was `compressed,dataless` at the end.

## What a fix would do (not done here; rule 5a(4) check first)

The prefetcher skips a file whose stamp is dataless and renders inside the thread guard (the race closed as
`ContentIndexer` closes it). The viewer and preview follow whatever the owner rules: the Notes precedent
(`W49.notes-s007-fix`) stats first, opens inside the guard, and offers "Download and Show".
