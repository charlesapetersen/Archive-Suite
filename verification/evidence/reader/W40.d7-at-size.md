## Promises tested

From the ledger, written before the code was read: R-02 "about 102k PDFs walk in about 10 s"; R-11 full-text
search of the whole archive; R-13 the table "stays smooth at 40k rows or more"; R-40 the health popover. The
plan asks for FTS build time, search latency, list scrolling, the popover's cost and memory, against the
2026-08-10 numbers in Reader `KNOWN_ISSUES.md`.

**What "smooth" is taken to mean here:** main-thread work in response to one user action. About 100 ms is where
a pause becomes visible; a second or more is a beachball. These thresholds are the yardstick, not something any
guide states.

Within ~10% on time, which is the run-to-run spread the August section already reports. The footprint

files walk in 0.45–1.3 s. **R-02's "102k in about 10 s" holds** with room to spare: 150k files take 7–10 s.

### Content index and search (the real sample)

| | Debug | `-O` |
|---|---|---|
| Index build, 5,268 real PDFs, through `libraryDidChange` → `ContentIndexer`, one pass | 9.27 s (1.8 ms/file) | 9.15 s (1.7 ms/file) |
| Index on disk | 29.6 MiB | 29.6 MiB |

The projection is linear in files. Extraction has no cross-file state, so linear is the natural model, but it is
an inference, not a measurement: the FTS merge cost grows faster than linear and is not in it.

Search, `ContentIndex.searchRanked` (the call the OCR field makes: all paths plus snippets for the top 300), `-O`
median of 5 (3 at 102k). The **102k** column is the sample's own extracted text replicated under distinct
paths to 102,478 rows, the corpus's PDF count (`write+optimize` 11.6 s, 496 MiB). Real words in real proportions;
the corpus's vocabulary beyond the sample is missing, which flatters rare words if anything.

**Where the time goes**, at 102k (`-O`): the same MATCH without snippets (`ContentIndex.search`) takes 24 ms for
`Bureau of the Budget`, against 42.0 s for `searchRanked`. Everything else is `snippetMap`, the `snippet()` call over
the top hits: about 200 ms a hit [I: total ÷ hits]. For single terms snippets cost about as much as the match
(`the` 417 ms of 679 ms; `Kennedy` 19 of 36 ms).

**R-11 is broken at corpus size for multi-word queries that contain common words:** 42 s for a four-word
phrase. The query runs on the `ContentIndex` actor, so the window does not freeze. But the result takes 42 s,
and every later query (and every other call on the actor) waits behind it. Single distinctive terms are fine
(11–146 ms at 102k). Filed as **`W40.fix-reader-fts-snippet-stall` (S2)**.

### The list at 115,999 rows (150k synthetic tree)

| Main-thread work | Debug | `-O` |
|---|---|---|
| `LibrarySort.sorted`, default (date, then name) | 2,496 ms | 970 ms |
| … by name | 1,666 ms | 959 ms |
| … by date / quality / read state / type / file tags | 5.1–6.7 s | 4.0–5.5 s |
| Filters (unread, name text, subject, year range) | 40–103 ms | 7–33 ms |
| `NavigationModel.recompute()` (filter + sort + duplicate names + selection + view state) | 2,726 ms | 1,021 ms |
| First `files` publish → list (signatures, folder tree, recompute) | 3,601 ms | 1,645–1,757 ms |
| **One tag edit** → list (`files` reassigned with one row rebuilt, as `applyVerifiedWrites` does) | not run | **1,561 ms** (max 1,602) |
| Table: first snapshot of every id | 507 ms | 477 ms |
| Table: per-change refresh with ids unchanged (`updateNSView`'s map rebuild + compare) | 182 ms | 107 ms |
| Table: snapshot after a re-sort (every row moves) | 356 ms | 342 ms |
| Table: `syncSelection` of one row (walks every id) | 56 ms | 43 ms |
| Table: scroll-to-row lookup (`firstIndex(of:)`, last row) | 39 ms | 29 ms |
| Health popover, `dataQuality` (recomputed on every access) | 116 ms | 30 ms |

The non-date sorts are slow on this tree because most of its rows tie on the key (seven tag sets), so most
comparisons fall through to the final tiebreak: `a.url.path.localizedStandardCompare(b.url.path)`, which builds
two path strings and runs an ICU comparison each time. The real corpus has more distinct dates, so its
date sort will tie less. The default sort, which ties into the name and almost never reaches the path, still
costs ~1 s at `-O`: that is `localizedStandardCompare` itself, about two million times.

**R-13 is broken at this size:** every Mark Read, inline edit, group edit, rename and undo reassigns `files`
(`ArchiveLibrary.applyVerifiedWrites`), and `libraryDidChange` runs `recompute()` on the main thread each time.
At 116k rows that is 1,561 ms at `-O`, before the table's own per-change refresh. Changing the sort column costs
1–5.5 s. Filed as **`W40.fix-reader-list-recompute-at-size` (S2)**. At the promise's own 40k the
cost would be about a third [I: `n log n`, not measured], which is still visible.

**Scrolling** was not measured as a frame rate: the unit host draws nothing, and a 116k-row tree is not in the
VM. What was measured is the cell work: making and sizing every visible column's cell for a 35-row screen, at
200 offsets across the list. At `-O` that costs a median of 95 ms, p95 102 ms: **2.7 ms per row**. Without a window
the table's reuse queue is empty, so every cell is built new, which makes this an upper bound. A real scroll
frame builds only the rows it exposes, a few per frame, so it fits a 16 ms frame. The first runs reported
4–7 ms per row. That was the harness, not the app: the 63,000 cells it built were kept until the case ended, and
memory pressure slowed the rest. Wrapping each screen in an `autoreleasepool` removed it. A cell's cost does
not depend on how many rows there are. **Not filed.**

**The health popover (R-40)** costs 30 ms at 116k rows (`-O`), 4 ms on the sample. Fine. The popover itself was not
opened (no UI was driven), so the row stays `unproven`.
