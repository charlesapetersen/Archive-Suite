# S-005 — independent check of the password-protected PDF warning

2026-11-21 · Codex (gpt-6.2-sol, medium) · baseline `ba39eeb4` · macOS 27.2.1, Xcode 27.2.
The original reproduction was by Claude Opus 5.5 in `dea883c7`.

## Method

1. Create a synthetic two-page PDF using ReportLab 4.4.10. Draw “Independent S005 selectable text”
   on page 1 and “Second text page” on page 2. Make an encrypted copy using qpdf 12.3.2:
   `qpdf --encrypt fixture-pass fixture-owner 256 -- plain.pdf locked.pdf`.
2. In a temporary app-hosted unit probe, verify with a separate PDFKit instance that the copy opens
   encrypted and locked, then unlock it with the test password and verify its first-page text.
3. Load the plaintext control and the locked copy in turn with
   `DocumentViewerModel.load(DocumentSelection(filePaths: [path]))`, the entry point called by
   `DocumentWindowView`. Use a non-persisting viewer model. Read the PDFKit state, `loadError` and
   `formatNote` without supplying the password to Reader.

## Observed result

| Opening | Page count | Readable first-page text | Load error | Viewer banner |
| --- | ---: | --- | --- | --- |
| Plaintext control | 2 | Yes | None | None |
| Password-protected copy | 2 | None while locked | None | “No OCR text layer — this document is image-only, so text search and copy won’t work here.” |

The password check verified selectable text in the encrypted copy once it was unlocked. Reader kept the
copy locked and gave no password message. `DocumentWindowView` displays `formatNote` directly as its
banner. The existing `EncryptedPDFSuspectTests` also ran: the indexer marked its separate locked
fixture `.unreadable`, and the viewer check recorded the expected failure.

The independent check confirms the viewer defect. The follow-up is `W49.fix-reader-encrypted-pdf`.

The headless Reader smoke suite reported 1,076 tests, with six skipped and no failures. The
independent probe produced no compiler warnings. The probe and synthetic inputs were temporary.
