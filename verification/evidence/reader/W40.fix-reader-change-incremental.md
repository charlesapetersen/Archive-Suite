## Where the time goes now (run 3, -O; run 2 alike)

- **Foreign change:** `library.apply` 0.4 ms (was 5,942 ms: a dictionary of every row, a filter of every row per
  path, a re-sort of every path); `model.applyRowChanges` 13 ms; the table's `showRows` (emulated) 8 ms (was 79 ms,
  twice); smart-folder counts 0.1 ms (was 1,224 ms, 20 full counts on main). No indexing pass, format-status read,
  prune or second recompute starts.
- **Reader write:** `library.applyVerifiedWrites` 0.4–0.5 ms (was 105–126 ms); `model.applyRowChanges` 4–7 ms;
  `model.refreshUndoHistory` 2–5 ms; `model.reverifyCacheRows` 1–5 ms.
- What is left in `applyRowChanges` is one copy of `displayed` (now a pointer per row, since `ArchiveFile` keeps its
  fields in one shared box) and the row predicate's setup.

Run 1's 74 ms was that copy before the box: copying `displayed` (49 ms) and the table releasing the old copy (27 ms),
each about a dozen retains and 300 bytes per row at 116k rows.

## Memory

Run 3: the footprint after 200 tag edits and 200 file switches, and after a quiet minute, was 484 MiB against 485 MiB
at the start of the memory phase; run 2 ended at 481 MiB against a 556 MiB start. Either way the edits leave nothing
behind; W40.reader-scale-measure measured +228 MiB on the same lane (the whole-library copies the allocator kept; a
patch now copies no rows, and a whole-list copy is a pointer per row). `leaks`: 194,456 leaks, 16.5 MB, as before
(one `CGPDFContentStream` per PDF the first index pass read; not the Reader's code, not growing).

## Correctness

- `LibraryRowPatchTests` (unit, every run of the bundle) holds each patch to the whole rebuild it replaces: 40 random
  watch batches (tag changes, removals, new files, unreadable and folder paths, a file replacing a folder of rows,
  verified writes newer than the read; composed and decomposed folder names; libraries of 200 and 1,200 rows) give
  the same `files`, phase and verified-write count through the patch as through the whole merge, and a change set
  naming exactly the rows that changed; 125 random Reader writes over five views (filters, sorts by read state, tags
  and date, a smart folder) give the same `displayed`, selection cache, ambiguous-date count and duplicated names as
  `recompute()`, and the same smart-folder counts as a fresh count; `LibrarySort.before` agrees with
  `LibrarySort.sorted` on seven sorts.
- Tier-2 review (two Opus passes, read-only): no defect in the merge equivalence, the row lookups or the TagWriter
  path. Fixed from them: an ambiguous-date count applied twice when a recompute lands between a change and its patch
  (the list now records the library revision it was built from); whole-array copies on the hot path (the box); a
  superseded rebuild that left the next patch without its signatures and counts (it now forces a rebuild); counts
  moved by a delta they already held (counts record the revision they were taken at). One suspicion did not hold:
  the file-system representation of a file URL equals its `path` byte for byte, measured for both URL constructors
  and NFC and NFD names, so the patch and the index key paths alike.

## What still takes the whole-library path

A change that adds or removes a library row (a new tagged file, a file whose Read/Unread tag was removed), a
content change (the index must read the file), a folder (subtree) read, a path with rows under it, and a re-walk.
They are correct, as before, and no longer pay a re-sort of every path when the batch is path-local: a new or
removed row is placed by binary search. A tag change after one of them may recount the smart folders once, off the
main actor, because the counts no longer match the revision it starts from. They still run the model's whole rebuild
(recompute, indexing, format statuses), which W40.reader-scale-measure measured at 85–102 ms for the presentation
at -O. Not in this item's budgets, and not filed: no owner report points at them.

## Limits

As in W40.reader-scale-measure: a synthetic tree with no text (the two OCR folders count 0), emulated views, and the
heavy lock held for the run. Selection (arrow keys 95–121 ms) and the document window (218 ms) are the other two
items' budgets and are unchanged here.
