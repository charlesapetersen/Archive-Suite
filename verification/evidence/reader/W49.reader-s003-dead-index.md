# W49.reader-s003-reproduce — a dead content index answers an OCR query with "No matches"

Suspect `S-003` (`verification/SUSPECTS.md`), 2026-11-20, Opus 5.5. Reproduced, by a unit test of the shipped
model on scratch data: `ArchiveReaderTests/DeadIndexEmptyListSuspectTests`.

## The code still says what the suspect says (rule 5a(1))

| Step | Where | What it does with an unopenable index |
|---|---|---|
| The query | `ContentIndexer.searchRanked` (`Search/ContentIndexer.swift:453`) | `openForQuery` fails, records `.unavailable`, and returns `RankedSearch(paths: [], …)`: an empty answer, not "no answer" |
| The model | `NavigationModel.runFullTextSearch` (`Views/NavigationModel.swift:1468`) | a non-nil result, so `ftsPaths = []`, and every row is filtered out |
| The overlay | `LibraryEmptyState.forPhase` (`Search/LibraryScan.swift:186`) → `NavigationWindowView` `.filteredOut` (`Views/NavigationWindowView.swift:393`) | rows exist and none are displayed, so "No matches", with `emptyListExplanation` blaming the OCR search |
| The warning | `NavigationWindowView` status bar (`:909`) | the amber "Search index unavailable" line, one line at the foot of the window |

Nothing between the indexer's failure and the overlay asks whether the index is dead. The overlay names the search
as the cause and offers "Clear Text", which reads as an answer.

Not deliberate (rule 5a(3)): `openForQuery`'s own comment says a dead-index query "otherwise degrades to an empty
result the user reads as 'no matches' (W23.m9)", and W23.m9 put the warning in the status bar for that reason. The
"No matches" overlay with its sentence came later (`W40.fix-reader-filter-bar`), and nothing in it looks at
`indexFailure`.

## The run

Scratch root in `NSTemporaryDirectory()` with two tagged files; the indexer pointed at a scratch index file of
1 KiB of `0x5A` bytes (the same garbage `ContentIndexerFailureTests` and the VM fixture's `AR_GUI_CORRUPT_INDEX=1`
use: SQLite opens it and fails on the first statement). Both files listed, then the OCR query "smith":

- `indexFailure` = `.unavailable`, message "Search index unavailable" (the status line is drawn);
- `ftsPaths` = `[]`, `displayed` empty;
- `LibraryEmptyState.forPhase(…)` = `.filteredOut`, the "No matches" overlay;
- `emptyListCauses` = `[.text]`, `emptyListExplanation` = "The OCR search “smith” hides every file."

The check that the overlay is not `.filteredOut` is an `XCTExpectFailure`, so the bundle stays green until a fix
removes it. `xcodebuild test -only-testing:ArchiveReaderTests/DeadIndexEmptyListSuspectTests`: 1 test, passed
(0.23 s), no new warnings.

## What it does not show

The run checks the model state the window reads, not pixels. The view's switch from that state to the overlay is a
plain `switch` on `LibraryEmptyState` with no other input. The VM route the suspect names
(`ContentIndexFailureUITests` with the corrupt-index fixture: type an OCR query before the repair, screenshot the
list) would show the same thing drawn; the independent check may take it.
