# W40.reader-scale-measure — the chain behind one change, at corpus size, Debug and -O

- **Date:** 2026-11-11 (runs 00:35–02:00 PST).
- **Code:** `ReaderStages` signposts (`ArchiveReader/macOS/Sources/ArchiveReader/Core/ReaderStages.swift`) and
  `ReaderChainAtSizeTests`, both landed in this item; the stages measured are listed per scenario below.
- **Command:** `ops/scale/run-reader-at-size.sh --only chain` (Debug, `-Onone`, twice) and `… --only chain --optimized`
  (`SWIFT_OPTIMIZATION_LEVEL=-O`, as Release builds). Reports: `~/Library/Caches/ArchiveSuiteScale/reader-chain{,-O}/report.txt`.
- **Machine:** Mac15,7 (M3 Pro, 12 cores, 18 GiB), macOS 27.2. The test host is app-hosted and draws nothing.
- **Tree:** an APFS clone of the 150k synthetic tree (`scale-corpus-150000-chain`, made in 28 s and deleted after each
  run): 150,000 files, **115,999 listed**. The library ran live, with its real walk and its real FSEvents
  `CorpusWatcher`, a scratch content index, a scratch audit ledger and a throwaway defaults domain. The real corpus was
  not read. The document window's files were 5 PDFs from the W40.c2 sample, read only. The sample was listed before
  and after each run by the harness, and it was unchanged every time (9,315 paths, listing SHA-256 `62801cd97755a85a`).
- **Smart folders:** 10 saved. Unread 63,102; Box 12 32,066; Correspondence + Read 13,995; Memoranda 18,071; 1970s
  18,071; Undated 97,928; Quality 3 0; name contains "1" 71,149; and two with OCR-text rules (`budget`;
  `memorandum Treasury` + Unread), which count 0 because the synthetic PDFs have no text. Those two therefore measure
  the query round trip and the row test, not FTS posting-list cost. W40.d7's `search@102k` has that cost: 10–430 ms
  a query, on the content-index actor, off the main thread.

## How it is measured

- **main-busy.** A background thread sends one main-queue ping at a time and times its return. Every ping held for more
  than 4 ms is added up. This counts blocking I/O on main as well as CPU. Main-thread CPU (`thread_info`) cannot be
  used here. While an async test awaits, XCTest's waiter spins the main run loop, and that read 990 ms of main-thread
  CPU per idle second.
- **longest stall.** The longest single ping, which is the beachball the owner sees.
- **visible.** The time from the trigger until the list republishes (`displayedGeneration`). For selection changes
  it is the time until the selection cache holds the new set. For the viewer it is the time until the new document is
  loaded and its panes are drawn.
- **settled.** The time from the trigger until the last stage of the chain ended. A chain counts as quiet after 3 s
  with the index idle and no stage ending (1 s for selection and viewer changes).
- **stages.** `ReaderStages.measure` totals, per stage and per thread kind. Nested stages are inside their parents:
  `presentation.build` runs inside a recompute, for example.
- **Emulated views,** named `view.… (emulated)`. Each runs once per main-queue turn after a publish, which is when
  SwiftUI would run it:
  - the library window's inspector (`TagEditorView` → `libraryFiles(atPaths:)` over the selection);
  - the table's `showRows` and `syncSelection`;
  - the document window's own inspector on its open file;
  - its two panes, each drawn from a page copy at 900×1200 (`PDFPaneView.show` copies the page; PDFView then draws tiles).
  The pane figure is a stand-in for PDFView's drawing. It is not PDFView itself.
- **Foreign change.** `/usr/bin/xattr -wx com.apple.metadata:_kMDItemUserTags …`, run as a child process, because the
  watcher drops this process's own events (`kFSEventStreamEventFlagOwnEvent`). Each foreign change flipped Read and
  Unread on one listed file, at ¼, ½ and ¾ down the list.
- **Reader write.** `NavigationModel.mark(.read/.unread)` on the selection (1 or 20 rows), inside the Box 12 smart
  folder (32,066 rows). It goes through the real TagWriter path: verify, two `F_FULLFSYNC`, audit.

**-O is materially faster on the chain**: 1.5× on the foreign change, about 4× on a Reader write, and 1.4–1.6× on

`--debug` keeps the Debug build.

## Where the time goes (-O; Debug in brackets)

**Foreign tag change, 1 file**

- `library.apply (watch batch)`: **5,942 ms** [7,158]. One FSEvents batch builds a dictionary of every row and
  filters all of them per changed path. Then it **re-sorts all 115,999 rows by `localizedStandardCompare` of their
  paths**, on main. String collation is system code, so -O barely helps.
- `model.countMatches.rows`: 1,224 ms [4,781], 20 calls. These are the 10 smart folders counted twice. The first
  count comes from the match-facet signature changing. The second comes from the index pass that the tag change
  starts: its end calls `refreshFormatStatuses`, which re-counts. Each call tests every row; the largest takes 226 ms
  [1,055].
- `presentation.prepare`, off main: 102 ms [1,069]. `presentation.build` on main: 85 ms [907]. The build is the second
  `recompute()`, after the format statuses arrive.
- The table's `showRows` (emulated): 79 ms [157], twice.
- Everything else is under 5 ms.

**Reader write in a smart folder, 1 file (20 files)**

- `model.countMatches.rows`: 1,218 ms (1,203) [4,803]. The same 20 calls.
- `library.applyVerifiedWrites`: 105 ms (126) [1,103]. This is a `compactMap` over all rows, done once per write.
- The inspector's `libraryFiles(atPaths:)` (emulated): 75 ms over 7 publishes (307 ms with 20 selected) [364 / 665].
  A linear scan runs on every publish.
- `presentation.prepare`, off main: 52 ms. `presentation.build`: 31 ms.
- `model.pruneSelection`: 31 ms. `model.selectionCache`: 22–35 ms. The table's `showRows`: 22 ms.
- `tagWriter.writes`: **26 ms for 1 file, 76 ms for 20**. This is the file-safety cost (two full fsyncs per action
  plus the verify re-read). It stays, and the budgets below are measured after it.
- `model.refreshUndoHistory`: 1 ms (21 ms in Debug on the first write).

**Selection, -O**

- `model.selectionCache`: 91–116 ms, whatever the selection size. It filters all 115,999 displayed rows through
  `Set<URL>.contains` and sorts the survivors. URL hashing is what costs.
- The inspector's `libraryFiles(atPaths:)`: 11 ms for 1 selected, 14 ms for 500, 41 ms for 501.
- `moveSelectionInList.find`: 99 ms. It maps every displayed id.
- `persistSelection`: 1–2 ms. The table's `syncSelection`: under 1 ms.

**Document window, next file, 5 open, -O**

- The panes' page copy and draw (emulated): 188 ms [146 in Debug: PDFKit and CoreGraphics are system code either way].
- The document window's own inspector (emulated): 53 ms. A full linear miss: the sample files are not in the 116k
  library.
- `viewer.loadDocument`: 3 ms. `PDFDocument(url:)` is lazy.
- `viewer.jpegPartner`: under 1 ms. No JPEG index was configured.

## Memory over a session: 200 tag edits and 200 file switches

Each step marked one file Read or Unread (200 different files across the list) and then moved the document window to
its next file. Footprint is the in-process `phys_footprint`. `footprint`, `heap` and `leaks` were run on the test host
from the harness's process.

| | -O | Debug, run 1 | Debug, run 2 |
|---|---|---|---|
| footprint at start (116k listed, indexed, 10 folders) | 492 MiB | 540 MiB | 473 MiB |
| after 20 steps | +245 | +73 | +155 |
| after 40 … 200 steps | +224 … +265, no trend | +72 … +73, flat | +140 … +182, no trend |
| after a quiet minute | +228 (−0 from the busy end) | +72 (−0) | +142 (−0) |
| `heap` live bytes, start → end | 407.9 → 456.3 MB (+48) | 406.2 → 456.9 MB (+51) | 408.7 → 470.8 MB (+62) |
| live nodes, start → end | 2,154,799 → 2,149,545 | 2,154,007 → 2,149,602 | 2,153,693 → 2,149,588 |
| Malloc Small dirty / reclaimable at the end | 352 / 373 MB | 340 / 381 MB | 327 / 400 MB |
| Malloc Large dirty, start → end | 131 → 344 MB | 180 → 248 MB | 115 → 264 MB |
| `CollationRanks` strings | 115,999 throughout | 115,999 throughout | 115,999 throughout |
| peak footprint | — | 898.5 MB (first index pass) | — |

The plateau's height varies between runs of the same build (+72 and +142 MiB in Debug). Its shape does not: it is
reached within 20–40 steps, it does not trend afterwards, and a quiet minute returns nothing.

**Reading it:**

- **No leak in what this lane drives.** Growth stops within 20 steps, and the live node count falls. What `heap`
  shows as new since the start is whole-library copies: one or two `[ArchiveFile]` buffers of 20.8–46 MB, a 4.4 MB
  `[String: PDFFormatStatus]`, and about 70–90 MB of untyped 4.2 MB blocks of the same size class. The old copies were
  freed.
- **The cache is not the cause.** `CollationRanks` stays at the library's own 115,999 strings, since no edit adds a
  path.
- **What remains is the allocator keeping freed memory.** About 370 MB of Malloc Small is reclaimable but held.
  Malloc Large dirty grew by 213 MB (-O) and 68–149 MB (Debug), while live heap bytes grew only 48–62 MB, so most of
  that growth is freed large blocks still held dirty. These are the whole-library temporaries of cause A
  (every edit allocates and frees several 116k-row arrays). A quiet minute returns none of it. That is fragmentation
  and retention, not growth. Fewer whole-library copies (W40.fix-reader-change-incremental) is the fix.
- **`leaks`:** 194,090 leaks for 16.5 MB at -O (Debug: 194,513 and 194,198, both 16.5 MB). Of these, 96,355 are
  `CGPDFContentStream` (80 bytes) and 19,383 are `CGDataProvider` clusters (448 bytes). That is about one per PDF
  read by the first index pass (PDFKit text extraction), and it does not grow with edits or switches. It looks like
  CoreGraphics' own allocations, not the Reader's code, and at this size it is not what the owner sees.
- **Not reproducible here: the views.** The owner's app at 6 h 19 min had IOSurface 332 MB in 96 regions and
  CoreAnimation 48 MB. This host draws nothing and showed 80 KB of CoreAnimation and no IOSurface. Real PDFViews'
  tiles, and growth with real OCR text (the FTS page cache, classifications), are outside this lane. The viewer item's
  memory budget is therefore measured with real views in the VM.

## Budgets set for the three fix items (on this lane, at -O)

- **W40.fix-reader-change-incremental**
  - A foreign tag change on one file: at most 50 ms main-busy, visible within 500 ms.
  - A Reader write on 1 or 20 files in a smart folder: at most 150 ms main-busy after TagWriter returns, visible
    within 250 ms.
  - No stall over 100 ms in either.
  - No `model.countMatches.rows` on the main thread.
  - The 200-edit run plateaus within 100 MB of its start.
- **W40.fix-reader-selection-at-size:** an arrow key (1 or 500 selected), ⇧-arrow (from 1 or 500) and the
  preview-sheet arrow each at most 16 ms main-busy, with the inspector and the table included.
- **W40.fix-reader-viewer-switch**
  - The next file visible within 100 ms main-busy with 5 open.
  - A 200-switch run ending within 100 MB of where it started, measured with real PDFViews in the VM.

## Also found

- **The Reader's Release build carried `com.apple.security.get-task-allow`.** Xcode injects it into a locally signed
  build. The root guide says Release must carry neither debug entitlement, and the Processor already opts out, so
  `CODE_SIGN_INJECT_BASE_ENTITLEMENTS: NO` is now in the Reader's Release config. Re-measured on the product
  (`codesign -d --entitlements -`): the sandbox, app-scoped bookmarks, user-selected read-write and executable, and
  nothing else; `codesign --verify --strict` passes. Notes and the DMG script check: `W40.release-no-debug-entitlements`.
- **The Release build has two pre-existing warnings**, at `ArchiveLibrary.swift:403-404` ("will never be executed",
  from the `#if DEBUG` constant). They are not from this item, and Debug is clean.

## Limits

- The tree is synthetic: tiny PDFs with no text. The two OCR-text folders count 0, and the first index pass (280–305 s
  for 116k files) measures extraction of empty files only.
- The views are emulated, as said above. The real table draws, and the real PDFViews tile.
- The document window's files are not in the library, so its inspector is a full miss. That is the worst case of a
  linear scan; a hit costs half on average.
- The harness holds the Mac-wide heavy lock, and nothing else heavy ran alongside.
