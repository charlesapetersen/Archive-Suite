# W40.fix-reader-tag-quarantine — why a sandboxed tag write stamps `com.apple.quarantine`, and what stops it

- **Date:** 2026-10-31.
- **Question:** `W40.d8` found that every Reader tag write added `com.apple.quarantine` (`0086;…;ArchiveReader;`)
  or ORed flags into another app's stamp (`0082;…;PDFpen;` → `0086;…`). What causes it, can a sandboxed app
  undo it, and does a different write primitive or entitlement avoid it?

## The probe

A 60-line Swift tool (not committed; rebuilt in a minute from the description), signed with
`Archive Suite Dev` and an embedded `Info.plist`, run from the host shell on scratch files in
`/private/tmp/qexp/files` (never the corpus). The files were made by the unsandboxed shell, so they started
with no quarantine xattr, except one given `0082;56940f8e;PDFpen;` by `xattr -w`. Access came from one of:
a temporary-exception absolute-path entitlement (what the Debug UI-test build uses for `/Users/`); a
`com.apple.app-sandbox.read-write` sandbox extension issued by the unsandboxed parent and consumed by the tool
(what a user's choice in an open panel grants); or a security-scoped bookmark the tool minted, resolved and
started (what the Reader does with its saved root on every launch).

## Results

| Process | Access | Write | `com.apple.quarantine` after |
|---|---|---|---|
| unsandboxed (the Processor's case) | — | tags | none |
| sandboxed | temporary exception | tags, label, raw `setxattr`, `fsetxattr` | `0086;…` added, every primitive |
| sandboxed | temporary exception | tags, then `removexattr` | `EPERM`; the stamp stays |
| sandboxed, `LSFileQuarantineEnabled = NO` | temporary exception | tags | `0086;…` added |
| sandboxed + `user-selected.executable` | temporary exception only | tags | `0086;…` added |
| sandboxed | user-selected extension | tags | `0082;…` added |
| sandboxed | bookmark scope | tags | `0082;…` added (production today) |
| sandboxed + `user-selected.executable` | user-selected extension | tags, label, `setxattr` | none |
| sandboxed + `user-selected.executable` | bookmark scope (+ temporary exception) | tags | none |
| sandboxed + `user-selected.executable` | user-selected extension | tags on a file stamped `0082;…;PDFpen;` | unchanged, `0082;…;PDFpen;` |

So the stamp comes from the App Sandbox on any extended-attribute write, not from `NSURL`'s tag setter, and a
sandboxed app cannot remove it afterwards. `com.apple.security.files.user-selected.executable` stops it for
writes under a user-selected or bookmark scope, and leaves another app's stamp alone. A temporary exception on
its own is not a scope, so the Debug fixture root now also starts one (`RootFolderStore.adoptTestRoot`: an
in-memory bookmark, never persisted). The Processor is not sandboxed and adds no stamp.

**Notes is left as it is.** It is sandboxed and writes tags through the same `CoordinatedTagWriter`, so its
writes are stamped too, but its only tag writes are onto its own `.md` note files (`NotesTagProjector`, never
the archive), where no promise like R-45 applies. Notes also has `network.client`, and the entitlement would
stop quarantining every file Notes creates in a store folder the user picked: notes, images, organisation
files. That trade buys Notes nothing, so it was not made (Tier-2 review).

**The cost in the Reader.** With the entitlement, files the Reader *creates* in user-selected folders are not
quarantined either. The only one is the root marker `.archive-suite-root.json`, and the Reader has no network
entitlement, so the defence given up is negligible.

## In the VM

Tart VM `archive-gui-runner`, off-screen, Debug build ad-hoc signed in the guest with the UI-test entitlements.

- `ONLY_TESTING=ArchiveReaderUITests/TriageJourneyUITests ops/gui/vm-gui-runner.sh reader xcuitest`, before the
  fixture stamp was added: `** TEST SUCCEEDED **`, 163.7 s; all 14 steps PASS with no expected failure left.
  On `f5c31a95` (W40.d8) the same steps stamped `0086;…;ArchiveReader;` on every written file.
- `ops/gui/vm-gui-runner.sh reader xcuitest` (whole suite), with `make-gui-fixture.sh` now stamping
  `0082;56940f8e;PDFpen;` on six files: 70 passed, 2 failed. The two are `LayoutGuardUITests`' light and dark
  runs on the tag cloud's `1983` field, which failed the same way on 2026-10-30 before this change
  (`W40.fix-reader-vm-suite-red`). The journey passed every step. It wrote unstamped files (`00004`, `00006`,
  `00008`) and stamped ones (`00007`, `IMG_NOTEXT`), and each file's quarantine xattr, or its absence, stayed
  byte-identical.
- Not run: `READER_JOURNEY=rehearsal`. The real-corpus sample is gone from the bench cache
  (`~/Library/Caches/ArchiveSuiteRehearsal/reader-sample`). The stamped synthetic files and the probe's PDFpen
  row cover the case it added.
