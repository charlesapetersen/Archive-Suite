## What was tested

The two real adoption paths: `RootFolderStore.setRoot` (the open-panel pick) and `RootFolderStore.init` →
`reResolveSavedRoot` (every relaunch). Both call `loadOrEnsureMarker` → `RootMarkerState.ensuring` →
`RootMarker.ensure` (`packages/ArchiveCore/Sources/ArchiveCore/Links/RootMarker.swift`), which writes
`.archive-suite-root.json` into the root with `Data.write(options: .atomic)` under an `NSFileCoordinator` write
claim. The write is on the write-surface lint's allow-list (`ArchiveReader/scripts/lint-write-surface.sh:112`), so
it is known to the code, but not to the Core Directive.

## Result: 4 tests green, four facts established

```
testChoosingAFolderWritesAnIdentityFileIntoIt                passed
testARelaunchReadsTheMarkerAndDoesNotRewriteIt               passed
testARemovedMarkerIsSilentlyReplacedWithANewIdentity         passed
testAFolderThatCannotBeWrittenIsStillOpenedAndRead           passed
Executed 4 tests, with 0 failures (0 unexpected)
```

1. **Choosing a folder writes a file into it (as suspected).** With no link copied and no tag edited, `setRoot`
   adds exactly one entry to the root, `.archive-suite-root.json` (a hidden JSON file under 512 bytes: a GUID, the
   folder's name, `kind: reader`, a creation date), and changes the root directory's modification time. The PDF's
   bytes (SHA-256) and tags are unchanged. Pointed at `~/Desktop/Google Drive/Archival Photos/`, this would be a new
   file at the top of the corpus, made on the first open. The Core Directive (`ArchiveReader/CLAUDE.md`) says
   Finder tags are "the *only* thing the app ever changes" and everything else is "strictly read-only"; it does not
   mention this file. The suite-level guides do not either.
2. **It is written once.** A relaunch on the same bookmark reads the marker; its bytes and modification time are
   unchanged.
3. **A removed marker is replaced without a word.** If the file is deleted (for instance by someone tidying the
   corpus), the next launch writes a new one with a different GUID. Every archive link copied before then names
   the old GUID, so it no longer resolves to this folder. Nothing tells the user.
4. **Reading does not need it.** A folder the Reader cannot write (mode 0555) is adopted and its files' tags read;
   only the identity is missing (`markerState` is `.degraded(.notWritable)`, and link copying says why). The marker
   serves durable archive links and nothing else. Notes only reads it (`ReaderRootStore` uses `RootMarker.read`,
   never `ensure`, on a Reader root).

## Not tested here

- Spotlight, Time Machine or a sync client noticing the new file. The corpus is plain local disk
  (not synced), so the only observers are Finder (hidden by the leading dot) and any script that lists the root.
- What happens to links when two copies of the corpus carry the same marker (a copied folder keeps its GUID).
  That is the durable-link design (`SPEC/`), not this write.

## Decision

The owner's call (Daemon Report, gate `W40.root-marker-owner-ok`) → `W40.root-marker`: keep the write and disclose
it in the Core Directive, write it only when the first archive link is copied (and disclose that), or keep the
identity out of the archive altogether.
