## What the iOS run does and does not exercise

The simulator has no camera and no `adb input`, so the app's DEBUG harness (`Debug/E2EHarness.swift`) stands in for
the operator: Android's file-drop seam at the shutter (`Documents/test_inject.jpg`), pairing from a launch payload
through `connectFromQR`, and a driver that calls the shutter's `capture(.document)`, `finishDocumentSegment` and the
tag sheet's Skip action. Everything from the shutter's completion onward is the real path: `persistCapturedJPEG`,
`addDocumentPhoto`, the durable queue, the LAN transport, segment-complete signals and their acks.

Not exercised: the buttons themselves (no touch is synthesised), the camera scan of a QR, auto-retry and Retry,
background uploads. Those wait for a UI test target or the borrowed phone (`W40.i5`, `W40.i4`).

## Defect found: the screenshots do not show the run (fixed in W40.i3-fu-shots, below)

All five screenshots of every `--ios` run are byte-identical, the launch-time frame ("Camera permission needed", no
thumbnail), although the app logged each capture. A screenshot taken after the run shows the real state ("Segment
ended · 1 page"), and a status-bar override appears in the very next screenshot, so the simulator's framebuffer is
live: the app commits no new frame while its driver runs. Holding each page until the script has its shot (the
`e2e-shot-N` handshake) and starting only once the app is `.active` did not change it. The script now checks that
the per-document shots differ and logs `WARN STALE screencaps` when they do not; it is a warning, not a failure,
until `W40.i3-fu-shots` finds the cause. Until then the iOS phone UI is not evidenced by these runs.

### W40.i3-fu-shots: the cause, the fix, the reruns (2026-10-22)

- **Probe.** A temporary DEBUG probe (since removed) counted display-link ticks and main-run-loop waits, and
  rendered the key window's own layer tree to a PNG at each step. At `captured 1` the run loop and display link
  were live (131 ticks, 201 waits) and the app and scene were `.active`, but the app's own layer tree still showed
  the launch frame. So the app was stale, not the simulator's framebuffer.
- **Cause.** In that probe run the app aborted, and the crash report showed where the main thread was:
  `CameraPreview.makeUIView` → `AVCaptureVideoPreviewLayer.setSession:` → `-[AVCaptureSession
  _commitConfigurationAndSkipWait:]` → `_buildAndRunGraph:` → `AVRunLoopCondition _waitInMode:untilDate:`, a
  nested run loop entered from inside SwiftUI's layout pass, at the moment `camera.authorized` turned true. The
  simulator has no camera, and the session's graph did not finish building while the run lasted. The driver's tasks, uploads and timers
  all ran on inside the nested loop, but the outer layout pass never ended, so no frame was committed. The abort
  itself was an AttributeGraph re-entrancy precondition from a layout flush inside that nested loop; the probe's
  extra work made it likely, and earlier runs did not abort.
- **Fix.** `CameraController.hasCamera` (nil until the session is configured, then whether it has a back-camera
  input). The capture screen attaches the preview only when it is true, and otherwise shows "No camera on this
  device." This is the same guard the QR scanner already had (it shows an "unavailable" message when there is no
  camera input). On a phone with a camera nothing changes, except that the preview appears once the session is
  configured, not as soon as permission is known.
- **Gate.** `e2e-phone-mac.sh --ios` now fails the phone side unless the connected shot and every page's shot
  differ (`STALE screencaps`). The warning is gone.
- **Reruns.** `/tmp/ap-e2e-shots4` and `/tmp/ap-e2e-shots5`: `RESULT: PASS`, with 5 distinct shots in each. Each
  `docN-captured` shows its own page's thumbnail in the strip, and `zz-drained` shows "Segment ended · 1 page".
  The iOS phone UI is now evidenced by these runs, within the limits of "What the iOS run does and does not exercise"
  above.
