# W40.i-usb-build — the iPhone cable route end to end in the simulator

- **Date:** 2026-10-31 (local) · **Source tested:** `9a8138e1` (W40.i-usb-mac `405f1295` + W40.i-usb-app) plus this
  item's harness change: `e2e-phone-mac.sh --cable`, `ios-sim-drive.sh`'s `IOS_E2E_CABLE=1`, and the app's DEBUG
  `ARCHIVECAP_E2E_CABLE=1`, which pairs through `connectCableFromQR` (the Connect screen's Cable path). No change to
  the upload path, the relay or the bridge.
- **Configuration/environment:** real Debug Mac app (`ARCHIVEPROC_HEADLESS=1`, pinned Gemini Flash-Lite route) with
  `ARCHIVE_USBMUX_SOCKET` pointed at `scripts/fake-usbmuxd.py`, which reports one USB device and satisfies each
  `Connect` by connecting to 127.0.0.1 on the byte-swapped `PortNumber`. The `ap-e2e-iphone` simulator (iOS 27,
  headless `simctl boot`; Simulator.app never opened) shares the Mac's loopback, so the fake's `Connect(48628)` lands
  in the real app's tunnel listener. The app is fresh-installed and pairs from an **empty-host** payload in Cable
  mode, so it has no address for the Mac except its own relay: every request goes URLSession → 127.0.0.1:48629 →
  verified tunnel → the Mac's `USBMuxBridge` → `CaptureServer`'s cable listener. Scratch output under
  `/tmp/ap-e2e-cable*` only.
- **Command:** `OCR_KEY=invalid-no-ocr-transport-only E2E_RUNDIR=/tmp/ap-e2e-cable4 KEEP_EMU=never caffeinate -i
  ArchiveProcessor/scripts/e2e-phone-mac.sh --ios --cable`.
- **Why an invalid OCR key.** An unattended session cannot read the Keychain's Gemini key: `security
  find-generic-password` waited on a permission prompt (run `cable1`, stopped). The cable route does not depend on
  OCR: the phone deletes a page only on the Mac's ingest ack, which comes before OCR. So this run proves the
  transport and says nothing about OCR; the OCR assertions fail by construction.
- **Result:** the app's log, in order: `paired`, `ready`, `captured N` / `ended N` for each of the three documents,
  `DONE 3` (nothing left on the phone, every ended segment acknowledged). The phone's screen reads "Connected · E2E
  Mac · cable" and "Connected over the cable" (`05-connected.png`); the five screenshots are distinct. The Mac
  finalized one collection, three PDFs, tagged `OCR Failed` + `Unread` (the invalid key). The fake usbmuxd served
  200 `Connect`s to the device, 176 of them refused (Result 3) while the app was not yet running, which is the
  top-up loop working as designed. Verdict `mac=1 phone=0 cable=0`: only the OCR token and year assertions failed.
  The LAN token appears in no artifact (`mac.log`, `REPORT.txt`, the fake's log, the script's output: 0 matches).
- **Wi-Fi unchanged:** `E2E_RUNDIR=/tmp/ap-e2e-wifi1 … e2e-phone-mac.sh --ios` (no `--cable`), same invalid key:
  the same verdict, `mac=1 phone=0 cable=0` (the cable check is off without `--cable`): `paired`, `ready`, three
  `captured`/`ended`, `DONE 3`, one collection of three PDFs, only the OCR assertions failing. The Wi-Fi route
  still pairs to `127.0.0.1:<port>` directly.
- **Not exercised:** the real usbmuxd's `Connect` forwarding, a device's network stack, the trust prompt, recovery
  after a lock, ATS on a device, and OCR. A run with a readable Gemini key (`OCR_KEY=…`, an interactive session)
  repeats this with the token assertions; the device checks are the iPhone pack's (`W40.i5-usb`, `W40.i4`).
