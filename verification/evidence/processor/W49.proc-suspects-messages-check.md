# Independent Processor checks for five misleading messages

2026-11-21 · Codex gpt-6.2-sol · product baseline `8e89c29b`. Claude Opus 5.5 recorded the
[first reproduction](W49.proc-suspects-messages.md) in `08f85025`.

The off-screen Tart guest drives Settings and Process Files using the same controls as a user.
The tests create their own JPEGs and destination folders and use a bundled CLI stand-in. A Debug-only transport
captures the app's already-built requests and supplies the replies. The key wizard uses the
headless Keychain refusal. Every input is synthetic and provider spend was $0.

```bash

```

## S-018 · Codex OCR ends before the promised retry

Process Files started on one synthetic page using Local CLI Agent and the bundled Codex stand-in.
The stand-in recorded every invocation, reported a reset 90 seconds after the first, and had
a transcription ready for any call made after that time. The retry sheet appeared. After
**Continue Without Retrying**, the run showed zero successes and one failure, with 86 seconds
left until the indicated reset. The automatic phase made one CLI invocation. The run log gave a
reset time and said the app paces to the subscription window and retries.

The source distinguishes Claude's usage-limit outcome in `LocalAgentClient.spawnAndClassify`.
The Codex and Gemini branch returns an ordinary failure to the pacing loop. This run
exercised Codex. The first reproduction had already shown a Claude stub wait and retry.

## S-024 · The key wizard leaves an empty field labeled Validated

In Settings → Accounts, the OpenAI row started empty with no status badge. The test opened
guided setup, selected OpenAI, typed a synthetic key and clicked **Validate key**. The mocked
model-list response returned HTTP 200, and the wizard offered to test OCR on a sample page.
The headless Keychain helper refused the save.

Immediately after closing the wizard, Accounts still showed no status badge. After switching
to General and coming back to Accounts, the OpenAI row showed **Validated** beside the empty
field with its **Not set — paste a key** prompt. This distinguishes the redraw timing from
the original headless reproduction, which directly asked the row which badge to show.
`ProviderKeyWizard.recordUsableKey` sets the flag even when the save returns false.

## S-025 · OpenAI preset contradicts its own help

In Settings → Reading, the test chose API Gateway and clicked **Fill in OpenAI preset**. The
visible Model ID was `gpt-5.4-mini`. Starting Process Files on one scratch page built a request
to `https://api.openai.com/v1/chat/completions` for that model, with `max_tokens: 8192` and
no `max_completion_tokens`. The transport returned a synthetic success.

The Reading panel says the preset fills a non-reasoning model. The built-in catalog marks
GPT-5.4 mini as reasoning-capable, and the fallback in `SettingsReadingPanel.openAIGatewayPresetModel`
selects that model. The gateway builds `max_tokens` in `OpenAICompatibleClient`. The direct OpenAI
adapter uses `max_completion_tokens`.

The public OpenAI model page confirms that GPT-5.4 mini supports reasoning and defaults to
effort `none`. The Chat Completions reference deprecates `max_tokens` and explicitly names
the o-series as incompatible. That reference leaves GPT-5.4 mini's live response to this field
unsettled. An OpenAI environment key and app Keychain entry were both absent.
[GPT-5.4 mini model](https://developers.openai.com/api/docs/models/gpt-5.4-mini) ·
[Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)

## S-029 · A failed comparative vote silently leaves a scan sideways

The two runs used identical text-free JPEGs with a blue bar marking the top of the upright
page. The image was presented sideways in both. Process Files used the one-vote comparative
mode and a synthetic successful OCR reply. The captured rotation request had four candidate
images.

| Reply to the vote | Vote requests | Blue bar in rendered PDF page 1 | On-screen result |
|---|---:|---|---|
| HTTP 200, correction D | 1 | 130 × 78 pixels, horizontal at the top | 1 succeeded, 0 failed |
| HTTP 500 | 1 | 60 × 102 pixels, vertical at the right | 1 succeeded, 0 failed |

The failed vote produced no rotation warning in the status or log. The pixel comparison
measures the embedded image because both PDF pages have a Letter-size media box.
`OCRProcessor.detectRotation` returns the Vision fallback in both comparative modes without
setting the unsure flag. The default agreement mode has a separate rule when a cloud vote fails.

## S-030 · Two failed jobs count as one

The test supplied a scratch folder to the normal drop handler, then clicked **Read Folders
Inside** and **Start**. Both files were named `same.jpg`, one in `a` and the other in `b`.
The transport recorded two OCR requests and gave each a distinct HTTP 400 reason. After
**Continue Without Retrying**, the visible status said **0 succeeded, 1 failed**. The log
said **Total files: 2** and **Failed: 1**. Its OCR failures section included one of the
two refusal reasons. The two visible file rows each showed their own refusal reason. The generated PDFs were `in/a/same.pdf` and `in/b/same.pdf`.

The log also has a separate section for pages whose image has no searchable text. Its
`same.jpg` entry describes Vision and carries no OCR refusal reason. The failure list in
`OCRProcessor+OCR.swift` uses the base name, and `OCRProcessor.writeLogFile` uses the first job
with that name. Separate failure counts and reasons require preserving each job's path.
The log-write error path remains untested.
