# Independent Processor spending checks

2026-11-21 · Codex gpt-6.2-sol · baseline `f2b51e98`. Claude Opus 5.5 recorded the
[first reproduction](W49.proc-suspects-money.md) in `325a3455`.

The off-screen Processor tests create JPEGs and separate output, backup and journal directories in
the UI runner's temporary directory. They use the real Process Files Start button. The capture case
feeds the synthetic JPEGs through the durable capture ingest and uses the real Live Capture handoff.
The model transport records the request route, model, decoded JPEG dimensions, byte count and SHA-256
after the app builds the request. It returns canned replies locally. The Gemini batch reply stops
after submission so the test measures the submitted image. The keychain is bypassed and the mock key
does not reach a provider. Provider spend was $0.

Run the four reproductions on the off-screen Mac guest with the project's shared heavy lock.

```bash
ARCHIVE_UNATTENDED=1 ONLY_TESTING=ArchiveProcessorUITests/MoneyJourneyUITests \
  ops/gui/vm-gui-runner.sh processor xcuitest
```

## S-039 · Stage for later offers the same photos again

The first **Process 2 →** click loaded `000001-doc.jpg` and `000002-doc.jpg`. Clicking **Start**
sent two OpenAI read requests and the run finished with two successes. Back in Live Capture,
**Process 2 →** was still enabled and handed off both files again. That click alone added zero
requests. A fresh app launch without the seeding switch recovered the same two photos. Its
**Process 2 →** and **Start** sent them again. Each of the two distinct JPEG hashes appeared
exactly twice across the four requests. The backup supplied the two recovered originals.

`LiveCaptureView.stageForProcessing` uses `CaptureSession.orderedFilesAndGroups`. The latter filters
filed and staged groups. A completed Process Files run leaves no handoff state for that filter.

## S-032 · Missing Gemini segmentation key appears after OCR

Three scratch pages used OpenAI for OCR, Automatic tagging and Gemini-only segmentation. **Start**
was enabled. After the click, the app built three OpenAI image reads, one per distinct photo, and then
showed **Segmentation could not finish** with “Gemini needs an API key.” The test pressed **Stop and
resume later**. Even without a saved Gemini key, the initial Start check let the reads proceed.

`OCRView.canStartProcessing` checks the OCR credential. The window stage checks the segmentation
credential later through `WindowStageTransport.make`.

## S-026 · Gemini batch sends a larger JPEG than direct OCR

Both runs used Gemini 3.8 Flash, the same 2000×1500 noise JPEG, 100% resolution and a 3 MB
standard size. Each used its own output folder and its real Start button.

| Path | JPEG payload | Dimensions |
|---|---:|---:|
| Gemini direct | 602,467 B | 985×739 |
| Gemini batch | 12,349,513 B | 2000×1500 |

The batch JPEG matched the source SHA-256 byte for byte. Its payload had about 20.5 times the
bytes and 4.1 times the pixels of the direct payload. These are image payload measurements.
The stand-in returned an HTTP 400 after recording the batch submission.

The direct call calculates a dimension scale from the file-size target in
`OCRProcessor.targetDimensionScale`. The Gemini batch builder passes the slider fraction directly
to the JPEG encoder. Both paths use the encoder's 2,048 px cap. The one scratch image tested here
was already within that cap. The original report also exercised a larger source.

## S-027 · Stored Batch changes a standard OpenAI run

With Batch off, the per-page reader menu was available. Selecting **GPT-5 nano for every page** sent
both reads to `gpt-5-nano`. With the stored Batch flag on, Settings disabled Batch and explained
that OpenAI has no batch API here. Process Files still showed two different estimates, $0.0105
standard and $0.0052 batch. The page-reader menu disappeared. **Start** sent two standard OpenAI
chat-completion requests to the run's `gpt-5.4-mini` model. Both runs used the same synthetic JPEGs.

`SettingsPagesOutputPanel.batchUnavailableReason` already disables the unsupported switch.
`OCRView.pageKindsActive`, `institutionalComputeActive` and the estimate still rely on the stored
flag. `OCRProcessor.startProcessing` suppresses readers and institutional imports on the stored
flag before later checking `provider.supportsBatch`. The import picker also disappeared with the stored flag on. The test measured the reader requests and the import picker's availability.
