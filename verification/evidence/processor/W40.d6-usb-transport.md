# W40.d6 — is the Live Capture USB transport reachable?

**Answer: yes.** A user path reaches `USBBridge`, and the tunnel it creates carries authenticated traffic to
`CaptureServer`. Run at `2154db2`, 2026-10-08, Processor Debug build, headless app + headless Android emulator
(`ap_test36`, `-no-window`). Raw run: [`W40.d6-usb-probe-REPORT.txt`](W40.d6-usb-probe-REPORT.txt).

## The promise (written before reading the code)

README §Live Capture: *"Android additionally supports USB with no shared Wi-Fi (the Mac auto-runs `adb reverse` so
the phone reaches `127.0.0.1`)."* Processor `CLAUDE.md`: `Net/USBBridge.swift` *"keeps `adb reverse` asserted so a
USB-tethered Android reaches `127.0.0.1:<port>`"*, with a re-assert on replug and on re-pair (B4-iii).
`LIVE_CAPTURE_ANDROID_TEST.md` Run B1 is the owner-facing manual check.

## The path in code

Mac, from the operator's click to `adb`:

1. Live Capture tab → **Start** (`Views/LiveCaptureView.swift:201`, `session.start()`; headless autostart calls the
   same `session.start()` from the view's `onAppear`, line 107–108).
2. `CaptureSession.start()` always starts the LAN server (`Capture/CaptureSession.swift:512`) — there is no
   transport picker to switch it off.
3. `NWListener` reaches `.ready` → `serverDidStart(port:)` (`Net/CaptureServer.swift:78`).
4. `serverDidStart` → `USBBridge.startReverse(port:)` (`CaptureSession.swift:561`): `adb start-server`, `adb reverse
   tcp:P tcp:P`, then the same `reverse` every 5 s. `serverDidStop` stops it; `phoneDidDisconnect` (a phone re-pair)
   calls `reassertNow()`.
5. `adb` is looked up at four fixed paths (`/opt/homebrew/bin`, `/usr/local/bin`, `~/Library/Android/sdk/platform-tools`,
   `/opt/homebrew/share/android-commandlinetools/platform-tools`). The app is not sandboxed (the entitlements file has
   no `app-sandbox` key), so spawning it is allowed under the hardened runtime.

Phone (Android `ArchiveCapture`): **Wired (USB cable)** on the connect screen (`ui/ConnectScreen.kt:66`) → scan the
Mac's QR → `CaptureViewModel.connectFromQr(wired = true)` replaces the QR's host with `127.0.0.1` and keeps its port
and token (`capture/CaptureViewModel.kt:323`). Manual entry in Wired mode pre-fills `127.0.0.1`.

## The run

`ArchiveProcessor/scripts/usb-reverse-probe.sh` (new, diagnostic only). Inside an Android device `127.0.0.1` is the
device itself, so a request to it reaches the Mac only through an `adb reverse` mapping — the emulator is a faithful
stand-in for the tunnel. The script never creates a mapping itself; every mapping it sees was made by the app.

| Step | Result |
|---|---|
| 1. App started with no device attached | listening on 48627 |
| 2. Emulator boots afterwards | app's heal timer created `tcp:48627 tcp:48627` on its own |
| 3. In-device `GET 127.0.0.1:48627/ping` | right token `200 OK`, wrong token `401 Unauthorized` |
| 4. `adb reverse --remove-all` (what an unplug does) | ping gets no answer; the app re-created the mapping after 3 s; ping `200 OK` again |

## What this does not cover

- The phone UI's Wired button was not tapped; its effect (host forced to `127.0.0.1`) is read from code and has no
  unit test. A full wired capture would need `android-ui-drive.sh pair` to grow a Wired mode.
- `e2e-phone-mac.sh` pairs the emulator over `10.0.2.2`, so the project's only phone↔Mac E2E has never exercised
  USB. This probe is the first runtime evidence for it.
- Real hardware (cable, USB-debugging prompt, a replug that changes the device serial) — `unverifiable-here`.

## Observations, not filed (no reproduction of a failure)

- If `adb` is installed anywhere other than the four paths, the bridge silently does nothing and the UI gives no
  sign that Wired is unavailable — the phone's Wired pairing would just fail its reachability preflight.
- The 5 s timer spawns `adb reverse` for as long as the server runs, device or not.
