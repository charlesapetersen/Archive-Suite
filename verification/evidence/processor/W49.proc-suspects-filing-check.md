The tests drive Process Files in the off-screen Tart guest with six scratch photo copies and separate
temporary output folders. Fresh Start uses a stand-in Local Agent CLI that returns one box, one folder,
and four document pages. Paid-batch Resume uses a completed scratch Gemini journal and in-process

```sh

  ONLY_TESTING=ArchiveProcessorUITests/ReviewDialogsJourneyUITests \
```

The three tests are `testCollectionMarkersWithSourceTags`, `testPaidBatchResumeReviewGates` and
`testCollectionNameConfirmedByClick`.

## S-034 · Source tags on collection labels

The runner stamped the guest copies with two Finder tags, `Scratch Subject` and `1978`. The app
selected **No tagging** and **Copy source file tags** in separate runs with Collection ID on. Both runs
confirmed the page and label reviews, then organized the PDFs. The test reads the Finder tag names back
from the source copies and output PDFs.

| Tagging selected | Box PDF | Folder PDF | Other PDFs |
|---|---|---|---|
| No tagging | Box | Folder | 4 with no tags |
| Copy source file tags | Box | Folder | 4 with both original tags |

Both label PDFs lost both source tags in Copy source. The other four outputs in the same run establish
that source-tag copying worked on the scratch inputs. The window showed the source tags beside all
six input rows and reported “Source tags copied.” The filed PDFs reveal the difference. Owner call 30 retains the Box/Folder markers in
both modes and requires all copied tags to survive. The relevant write is
`OCRProcessor.applyBoxFolderLabelTags` after collection segmentation.

## S-035 · Reviews after Resume Batch

The scratch batch represents the point after the batch's six OCR results and PDFs are already saved
and its provider chunk is consumed. The Debug fixture prepares the cached PDFs and saves the batch
using the real journal writer. After relaunch the
test follows the real Resume Batch button and watches each review through completion. The journal
holds Automatic tagging, Collection ID, name confirmation, and document review on.

The only reviews shown were **Review Collection Names** and the per-collection page review. The
whole-run page review, **Confirm Box & Folder Labels** and final tagging review never opened.
The app reported `Done. 6 succeeded, 0 failed. 5 segments tagged. 1 collections organized.`
All six PDFs were in the named collection folder and carried `Unread`. All four document PDFs
also carried the stand-in's subject tag. The relevant entry point is `OCRProcessor.resumeBatch`,
which builds segments directly from saved classifications and calls `performTaggingPhase`.

The comparison is an ordinary fresh Automatic + Manual run in the same UI test class, which shows
all three early reviews. Source inspection of `OCRProcessor.startProcessing` places the fresh paid
route before the same shared review calls. The separate [ordinary Resume evidence](W49.proc-s050-verify.md)
shows that ordinary Resume still displays final tagging review. Owner call 30 applies the same review
rule to both paths. The separate ordinary Resume check remains the gate for adding that case to the fix.

## S-036 · Typed name and Confirm and Organize

The test confirms an Automatic + Manual run's page, box/folder and tagging reviews. It edits the one
box name in **Review Collection Names** and clicks **Confirm and Organize** while the field is still
active, without pressing Return. The parent of the chosen output folder is inside the same disposable
test directory. The run saw the following on disk.

| Name typed | What happened |
|---|---|
| `a/b` | Six PDFs beneath `a/b/`. For example, the first PDF was `a/b/000001 a/b.pdf`. |
| Empty | Six loose numbered PDFs in the selected output folder. |
| `..` | Six loose numbered PDFs in the parent of the selected output folder and zero in the selected folder. |

The parent-folder run reported six successes and warned that it could no longer find the two
label PDFs where it had left them.

The path reaches `CollectionReviewRow` in `Views/OCRView+CollectionReviewSheet.swift`,
`OCRProcessor.applyReviewEdits` and `CollectionSegmenter.organizeOutput`. This is a filing destination
bug. The fix needs tests for both submitting the field and clicking the sheet button, as well as a
check that every file stays inside the chosen output directory.
