# Archive Processor: triage of 390 functions no run executed

Worktree: `suite-wt-20261126-044613-92066`. Paths are relative to `ArchiveProcessor/macOS/Sources/ArchiveProcessor/`.
Method: for each function, `rg -nw -t swift <base name>` over `ArchiveProcessor/macOS/Sources` and `packages/`, and
separately over `ArchiveProcessor/macOS/Tests` (the UITests). Generic names (`id`, `start`, `read`, `description`) and
closures were followed by hand. Nothing was built or run. The Processor's key-free drivers live inside `Sources`,
so a "caller" in a `*TestDriver.swift` file is a test, not a user path. Seven drivers failed partway on known main
defects (batch-resume, collection-organize, segmentation-chooser, entity-feature, run-quit-resume, settings-solver,
tagging-failure); a function after their failure point can show as never run for that reason alone. Where a
function's only callers are SwiftUI/AppKit views, it **may be reached by the pending UI run**.

**Most notable findings.**
1. **No run ever started Live Capture receiving (about 80 functions).** `CaptureSession.start`/`stop`, the LAN
   server's callbacks, the body reader (`CaptureServer.readBody`), the phone-connection timer, the whole Google Drive
   relay (51 functions: `DriveAuth`, `DriveClient`, `DriveObjectStore`, `FileRelayReceiver.start/tick/sweep`) and the
   page OCR a live session runs (`LiveCaptureProcessor.ocrTask`) never ran. The drivers skip the receivers.
   `FileRelayTestDriver` calls `scanOnce` directly, and the recovery driver swaps the paid read for
   `_recoveryTestOCRStub` (LiveCaptureProcessor.swift:1174). The livecapture journey and phone legs that would
   start a session were left out.
2. **The post-OCR tagging and review steps never ran (about 45 functions).** `performAutomaticTaggingWithReview`,
   `performManualSegmentAndTag` and `performCollectionSegmentation` (all called from OCRProcessor+PostOCRFinalizer.swift:87-123),
   the rotation review, `CollectionSegmenter` and the per-provider `classifyViaLLM` never ran. The collection-organize and
   segmentation-chooser drivers failed partway. `ReviewDialogsJourneyUITests` may reach some of this. No UITest touches
   manual per-segment tagging (grep for `manualSeg`/`ap.manual` in ArchiveProcessorUITests: no hits).
3. **Tools ▸ Read Box and Folder Labels (container label backfill, 33 functions) has no ledger row.** Only
   `ProcessorUITests` (around ProcessorUITests.swift:797) drives it, through canned reads, so the pending UI run may reach it.
4. **None of the paid batch clients ran (12 functions).** Submit, upload, cancel and retrieve for Anthropic,
   Gemini and Mistral need a key and money. The batch-resume driver failed. `PaidBatchUITestFixture`, the key-free
   stand-in, is wired only for UI tests.
5. **Two local readers never read a page.** Newspaper layout detection (`NewspaperPagePlan.prepare`, `NewspaperDetector.detect`) runs only
   when the driver gets `NEWSPAPER_MODEL_FILES` (scripts/test-newspaper-layout.sh), which this run did not set. The macOS
   on-device model reader (`OnDeviceModelClient`) never ran, although this host is macOS 27.
6. **Five functions look dead.** Nothing reads `ProcessorUITestConfiguration.inputDirectory`, yet 9 UITest files pass
   `-APUITestInputDirectory`. The `MacOSTagger.applyTags(_ GeneratedTags, to:stampUnread:)` overload has no caller.
   `ModelSelectionStore.savedModel`, `LocalModelSupervisor.residentPID` and `PendingRunSnapshot.visionTextThinkingLevel`
   have no caller either.
7. **Some features have no ledger row:** container backfill, Improve OCR, newspaper reading, the monthly spending
   limit, the label reader download, and Quit while a run is going.

No suspected bugs: nothing found while reading had enough evidence to claim one.
