# S-051 · Refused and interrupted batch creation

2026-11-21 · Archive Suite baseline `eaa9e556` · Codex `gpt-6.2-sol` · $0.

Claude Opus 5.5 first observed the 401 and uncertain-submission warning in the S-026 run. The original report is preserved. [Original run evidence](W49.proc-suspects-money.md#noticed-on-the-way)

The focused script drives the real Process Files `startProcessing` pipeline in Debug with one synthetic JPEG and Gemini Batch enabled. The test transport redirects requests to a loopback stand-in with a dummy key. One run receives a complete HTTP 401 with a provider error message. The other receives HTTP 200 headers and only the start of a JSON body, then the connection closes before the advertised length or a batch ID arrives. The driver records the final status, reads the on-disk recovery state and records the same banner text the view observes. It captures that state before test cleanup in a disposable state directory. [Reproduction script](../../../ArchiveProcessor/scripts/repro-batch-submission-outcome.sh)

## Cause

`GeminiBatchClient.createBatchJob` reads the 401 and throws the provider's error text through `OCRError.networkError`. The same error family also covers unreadable create responses. `OCRProcessor.performBatchOCR` logs the error and calls `reportInterruptedBatchSubmission` without passing it on. The message builder bases its zero-job wording on the number of acknowledged jobs and journal state, so a complete refusal takes the same path as an incomplete reply.

The README describes the uncertain warning for a job whose reply cannot establish acceptance. Keeping a journal when the reply is incomplete protects against a duplicate submission. An explicit authorization refusal of the first create can be reported as refused. A later refusal must preserve the IDs of any earlier acknowledged chunks. [Batch recovery guidance](../../../ArchiveProcessor/README.md#if-a-batch-submission-reports-an-uncertain-outcome)

## Observed result

| Stand-in reply | App log | Recovery journal | Pending-batch banner |
|---|---|---|---|
| Complete HTTP 401 | "Network error: Synthetic authorization refusal" | Kept, zero acknowledged IDs | Present |
| HTTP 200 with the body cut off | "The network connection was lost." | Kept, zero acknowledged IDs | Present |

Both runs reported the same status and produced zero PDFs. The loopback server saw one create POST per run. The original provider operation was Gemini's `:batchGenerateContent`.

> Batch submission outcome is uncertain. No server job was acknowledged, but a create whose reply was lost may still have been accepted. The recovery journal was kept, so Resume can pick the batch up. Review before retrying.

For a zero-ID journal, `resumeBatch` stops before polling and tells the user the journal has no recoverable server ID. The reproduction captured the pending banner headlessly through the app's state. Its Resume result was checked in the code.
