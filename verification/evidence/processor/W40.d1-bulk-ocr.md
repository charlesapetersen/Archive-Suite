## How it runs

`ArchiveProcessor/scripts/journey-bulk-ocr.sh` → `PROCESSOR_JOURNEY=bulkocr ops/gui/vm-gui-runner.sh processor
xcuitest`: the runner copies the box from the read-only rehearsal share onto the guest disk with `ditto`, hands the
key in through `tart exec -i` stdin to a 0600 file, and runs `BulkOCRJourneyUITests`, which only launches the app
with `ProcessFilesTestDriver`'s environment and waits for its marker. The driver runs the real Process Files
pipeline (`OCRProcessor.startProcessing`) with the shipped defaults where a headless run allows them: segmentation
approach Manual (the default: the OCR call classifies each page), merging off (one image, one two-page PDF), rotation
off, Automatic tagging, segment JSON on, no collection segmentation. Its auto-pilot accepts each review as proposed.
The runner deletes the key file, records the guest's own hex reading of every PDF's tag xattr, and brings the run
back with `ditto`. `scripts/journey_bulk_ocr_check.py` then checks every PDF (below).

The cost is stated first, by the app's own estimator with the inputs the Cost Estimate box uses (`estimate.txt`),
and a run estimated over the cap is refused. Every request passes through a meter on `NetworkSession`'s seam that
reads the reply's `usage`, refuses to send unless what is spent plus every request in flight (each priced at the
dearest call so far) stays inside the cap, stops after a reply it cannot price, and writes `spend.tsv`.

**Failure 1, reproduced: the date-evidence rewrite changes the source-name line** (`W40.fix-processor-evidence-rewrite-name`,
S3). The 36 failures are 18 PDFs, two each, and they are exactly the 18 that carry a `Date evidence:` line (an
estimated date taken from another page, e.g. `00009`: `estimate; from 00004 — RG 165.jpg; "August 1918"`). On
those the source-name line reads `00009 — RG 165.jpg` with an ordinary space where the file name and every other
output have U+00A0 (`00008 —\xa0RG 165.jpg`); the provenance failure follows from the name line not matching. The
rewrite (`OCR/PDFGenerator+DateEvidence.swift` `headerText`) rebuilds the header from the old page's parsed text
(`old.originalFilename`, read through PDFKit) rather than from the source's name, and the name comes back with an
ordinary space (where exactly the U+00A0 is lost is for the fix to pin down); its read-back check compares the new
header with the old parsed one, so it passes. The same 18 files, and only they, give qpdf's `object has offset 0` warning: the re-save
through `PDFDocument.dataRepresentation()` leaves a broken xref entry, which readers repair silently.

**Failure 2, reproduced: a reply that is not a reading is kept as the page's text** (`W40.fix-processor-non-reading-reply`,
S3). Qwen3.8 Flash refused 3 of the bench's 96 pages; here it gave 3 of 113 photos no reading. Their page 2 holds
the model's chatter instead of a transcription (`00028`: "The text provided in your prompt appears to be a
corrupted or heavily obfuscated string…"; `00034`: "The user wants me to identify the object in the image.";
`00073`: "The image shows a page from an archival file…"), no Classification line, and the job is `succeeded`. So
the run reports "113 succeeded, 0 failed", nothing flags the three pages, and the catalog's advice for this model
("give it a second reader for failed pages") cannot work: the page never counts as failed. Two of the three are
truth continuations and one a box label; they show as the run's 3 unclassified pages and two of its extra
boundaries (28, 34).
