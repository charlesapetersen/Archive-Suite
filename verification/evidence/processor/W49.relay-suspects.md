## S-021 · Android's Drive relay reports a segment signal as sent when the Drive write failed: reproduced

(1) The code still says it. `DriveRelayTransport.segmentComplete` (`ArchiveCapture/.../net/DriveRelayTransport.kt:88-93`)
calls `upsert` and returns `true`; `upsert` (`:34-40`) catches every exception, with a comment that holds for photos only
("no receipt → phone's receipt-wait times out + retries"): a segment signal has no receipt. `DriveClient.send` throws
`DriveException.Http` on any non-2xx. The caller, `CaptureViewModel.trySendSegmentComplete`, stops after the first
`true` and, through `sendAck`, removes the group from `endedSegments` and persists. iOS catches the throw and returns
`false` (`ArchiveCaptureiOS/.../Net/DriveRelayTransport.swift:70-78`).

(2) The operator's path, run by the real view model under Robolectric
(`ArchiveCapture/app/src/test/.../capture/DriveRelaySegmentSignalSuspectTest.kt`): a session restored with one page of
the open segment already on the Mac; pair to the cloud relay (`connectCloud`); End segment (`finishDocumentSegment`),
Skip on the tag sheet (`applyTagsAndContinue(null, null, null)`). The real `DriveRelayTransport` and `DriveClient` run
against `DriveRelayTransportTest`'s mock Drive (the Mac's folder and epoch marker in place), which answers the
`gdoc.segment.json` create with a 500. The one seam added is `CaptureViewModel.driveClientForTest`, test-only, in place
of the Google-signed-in client.

```
control (no failure):  gdoc.segment.json on Drive; endedSegments on disk = []
S-021  (create 500):   creates refused = [gdoc.segment.json] (one, no retry); no segment object on Drive;
                       endedSegments on disk = []; after a re-pair (connectCloud again): still one refused create
```

So the phone records the segment as delivered and never sends it again, even across a reconnect. The Mac then gets no
segment-complete for `gdoc`, so no tag card until Finish force-completes the group (`completeAllOpenDocGroups`), and the
phone's End-segment tags (quality, year, month) and its `seqs` snapshot (A5) never reach the Mac. That Mac-side
consequence follows from the code and from S-038's run below; it was not run with the phone test.

(3) Nothing calls it deliberate: the comment it rests on is about photos, and iOS does the opposite.

Also seen: `sessionComplete` (`:95-99`) swallows the same way, but nothing on Android calls it, so it has no effect today.

## S-038 · Over the Drive relay, Finish cannot wait for the phone to drain: reproduced

(1) The code still says it. `phonePendingActive` is set only by `updatePhonePending`, whose one production caller is
`POST /phone/status` (`Net/CaptureServer.swift:633-637`). `FileRelayReceiver` (the Mac's receiver for both the file relay
and the Drive relay, `CaptureSession.swift:491-502`) never calls it, and `SPEC/relay-object-format.md` defines no status
object. `proceedToFinishIfReady` (`Capture/LiveCaptureProcessor.swift`) holds on `phonePendingActive` alone for pages
still on the phone.

(2) `ArchiveProcessor/scripts/repro-relay-suspects.sh`: the built app headless on the file relay
(`LIVECAPTURE_TRANSPORT=fileRelay`), Apple Vision OCR, tagging off, settings as launch arguments (not persisted), all
in a mktemp folder. The script plays the phone with RelayObjectFormat's bytes: page 1 of document `g1` sent and
receipted, page 2 not yet written. The session-complete marker stands in for the Finish button: under
`LIVECAPTURE_AUTOFINALIZE` it runs the same `requestFinish` and drain gate. Then page 2 arrives.

```
page 1 of g1: receipted
page 2 of g1: still on the phone (not written)
Finish (session-complete marker) at 15:15:45
finalize: Finalized 1 collection · 1 files moved.          (15:15:46.9, about a second later)
PDFs filed: Live Capture …/000001 Live Capture ….pdf  (one photo: the suite's image page + text page)
page 2 of g1 arrives late at 15:15:47: receipted
PDFs after the late page: unchanged
backup/…/000002-g1.jpg, manifest: photos [seq 2, g1], filedGroupIds [g1]
```

Finish did not wait: document `g1` was filed with page 1 only, and the late page 2 stayed in the backup folder as a
page of an already-filed document (the "late page … kept in the Backup Folder, not this collection" path), outside the
collection. Over LAN the phone's heartbeat would have reported 1 pending and held Finish (`P-48`; the hold itself is
covered by `scripts/test-recovery.sh`). The Drive relay was not run (no Google account in a session); its Mac receiver
is the same `FileRelayReceiver` over a `DriveObjectStore`.

(3) Not deliberate as far as anything says. The 20-second staleness rule beside the gate is deliberate, but for a phone
that has gone silent; `P-48` promises Finish holds "until the phone's heartbeat reports nothing pending, so no segment
finalizes partial", and no document exempts the relay.
