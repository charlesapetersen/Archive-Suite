# W49.proc-fix-s045 — Live Capture names a document whose tagging call failed (S-045)

2026-11-26 · `ArchiveProcessor/scripts/repro-live-tagging-failure.sh`, headless on scratch paths · Claude Opus 5.5 · $0, key-free.

## What was wrong

`LiveCaptureProcessor.computeTags` called `TagGenerator.generateTags`, which drops the failure reason
`generateTagsReporting` returns (W49.proc-fix-s042). A document whose Automatic tagging call got an HTTP 500, or a
reply that was not the tag JSON, was filed with its OCR text, date and Unread tag but no subjects. Its row showed
success, and Finish said "Finalized 1 collection · 2 files moved." with no warning
([reproduction](W49.proc-s045-verify.md)).

## The fix

- `computeTags` calls `generateTagsReporting` on the Automatic document path and returns the reason with the tags.
  Boxes, folders, Mac-card subjects and manual mode make no call and report nothing.
- The reason is kept on the staged record (`StagedSegment.taggingFailure`). It is saved in the staging manifest, so
  it survives a relaunch, and kept through rotation-review regeneration, which reuses the first pass's tags. A
  Retry asks again and sets it afresh.
- **The row:** `labelStagedRecord` copies it to `SegmentStatus.taggingFailure`. The shared row shows an amber line
  on any state that is not failed: "No subject tags from the model: its tagging call failed (reason). Its text and
  date will still be filed." (`ProcessableItem.warningMessage`, which defaults to nil, so the Files pane is unchanged.)
- **Finish:** each filed document with a reason is named by the file it landed under, with the reason, in a "⚠️"
  note: "⚠️ 1 filed document's tagging call failed (000002 S045.pdf: Network error: HTTP 500: bad response), so it
  has no subject tags from the model. Its text and date were filed; re-tag it from the output folder (Process Files
  → re-tag)." So `summaryReportsProblem` is true.
- **What is filed is unchanged:** the same fallback tags, the complete OCR PDF, and the same filing and
  source-retirement decisions. `taggingFailure` is read only for labels.

## Tier-2 review

An adversarial review (Opus, read-only) found nothing serious. It checked the filing and deletion gates, every path
that builds or replaces a staged record, the order of the Finish note relative to the staged cleanup, manifest
decoding and isolation. Two low findings were fixed: Retry now clears the row's reason while it runs, and the row no
longer says "Filed" before Finish. Three were accepted:
- An older manifest restored without retained inputs shows no row line. Finish still names the document.
- A filed group with no landed PDF name would be named by its group ID. The reviewer did not find such a branch
  reachable.
- The filed-group-ledger failure summary omits the note. Its records stay staged, so the next Finish names the
  document.
