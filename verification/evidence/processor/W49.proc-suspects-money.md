# W49.proc-suspects-money — the Processor's four spending suspects: all four reproduced

2026-11-20 · `ArchiveProcessor/scripts/repro-suspects-money.sh` · $0. Every case is a real Process Files run through
`startProcessing` (`ProcessFilesTestDriver`, `PROCESSFILES_TESTMODE`) on synthetic scratch images in a mktemp folder.
The gateway route goes to the stand-in (`scripts/fake_gateway.py`) on 127.0.0.1; a direct provider's requests go there
too instead of to the provider (new switch `PROCESSFILES_REDIRECT_URL`), and `requests.tsv` records each as the app
built it: its address, body bytes, and each image's bytes and pixels. Phase rule 5a, one attempt each.

New driver switches, all DEBUG-only: `PROCESSFILES_STAGED` (inputs come from a Live Capture session in Stage for
later, as "Process N →" hands them over), `PROCESSFILES_SEGAPPROACH` (the chooser's approach, windows routed by the
production `WindowStageTransport.make` with no key), `PROCESSFILES_READER_MODEL` (every page given a reader),
`PROCESSFILES_BATCH_STORED` (the stored Batch flag passed on as `OCRView` passes it), `PROCESSFILES_REDIRECT_URL`.
The autopilot now records and answers the window stage's stop prompt (Stop).

## S-039 · Stage for later hands the same photos to Process Files twice: reproduced

(1) `LiveCaptureView.stageForProcessing` copies `session.orderedFilesAndGroups()` into the processor and switches tab;
nothing marks the photos. `orderedFilesAndGroups` leaves out only `filedGroupIds` and live staging's recovered groups,
which a Process Files run never writes.

(2) A Stage-for-later session received six photos as two documents, its backup folder in scratch:

```
── s039-first     handoff  session=2026-11-20T22-28-57Z  restored=0  files=6    stand-in calls: ocr 6
                  after-run   files=6
                  after-relaunch  session=2026-11-20T22-28-57Z  files=6
── s039-relaunch  handoff  session=2026-11-20T22-28-57Z  restored=6  files=6    stand-in calls: ocr 6
```

After the run the pane hands the same six over again. A relaunched app restores the session with all six photos, hands
them over, and the run OCRs all six again (12 OCR calls for six photos). Each hand-off still needs Start pressed in
Process Files; the button itself spends nothing.

(3) Nothing calls the repeat deliberate. README and REFERENCE say only that captures "hand off to Process Files for a
batch run". Keeping the photos is deliberate (the backup is the only copy once the phone deletes its own), so a fix marks
them handed off rather than removing them.

## S-032 · A segmentation approach with no key starts, and fails only after the OCR: reproduced

(1) The chooser says an unavailable approach "is gated where the run starts" (`Views/SegmentationChooserView.swift:39-41`).
`canStartProcessing` (`Views/OCRView.swift:1063`) has no segmentation term, and `startBlockedReason` gives none either.
The stage meets the missing key at `WindowStageTransport.make` (`Segmentation/RunSegmentation.swift:249-255`).

(2) Gemini in the chooser, no Gemini key, three photos on the stand-in's OCR route, Automatic tagging (the first
attempt ran No tagging, which never segments; that was a harness slip, not the suspect's attempt):

```
── s032-gemini-nokey   stand-in calls: ocr 3
  gate: boxFolderConfirmation
  gate: windowStop  pagesRead=3/3  Gemini needs an API key.
  status: Stopped before segmentation: Gemini needs an API key. Resume the run to continue where it stopped.
```

All three pages were read and paid for before the first word about the key. The run is resumable, so the reads are kept
if the user adds the key and resumes; they are not if the user changes the approach or starts over instead.

(3) The code promises the start gate in a comment, so the missing gate is not intended. No owner question.

## S-026 · Batch OCR scales by dimension, not size: reproduced, narrower than raised

(1) The direct path turns the slider into a per-file size target (`targetDimensionScale`,
`OCR/OCRProcessor+OCR.swift:1952-1957`). The batch path passes the slider straight to `loadImageAsJPEG(scale:)`
(`OCR/OCRProcessor+OCR.swift:845-859`; `OCR/BatchOCR.swift:85`, `:356`, `:859`), a dimension scale. Both cap the
long edge at 2,048 px (`ImageEncoding.maxOCRDimension`), and a JPEG already within the cap goes up as its own bytes.

(2) Two noise scans at 100%, the standard size 3 MB, Gemini 3.8 Flash direct and then batch, both redirected:

| scan | file | direct sent | batch sent |
|---|---|---|---|
| dense, 2000×1500 | 8,776,328 B | 904,450 B, 1169×877 | 8,776,328 B (the file itself), 2000×1500 |
| large, 6000×4000 | 41,835,195 B | 1,082,715 B, 1606×1071 | 1,963,467 B, 2048×1365 |

So batch sends a scan the direct path would shrink at a larger size, up to the 2,048 px cap: 9.7 times the bytes and
2.9 times the pixels for the dense scan, 1.8 times the bytes and 1.6 times the pixels for the large one. "A 10 MB scan
is sent whole" holds only when the scan is already within 2,048 px; larger scans are capped. Gemini (by tiles) and Anthropic
(by area) price an image by its pixels, so the batch reads cost more than the size-based estimate assumes. This run does
not measure by how much.

(3) Nothing calls the batch scaling deliberate. No owner question.

## S-027 · Batch mode is offered without a batch provider, and still changes the run: half cleared, half reproduced

(1) Half of the suspect is gone: the Batch toggle is disabled when the provider has no batch, and says why
(`Views/SettingsPanels/SettingsPagesOutputPanel.swift:59-68`, `:88`, W40.fix-processor-settings-backend-mismatch). But a
flag left on (set under Gemini, the provider then switched to OpenAI) is still passed on: `OCRView.startProcessing`
sends `batchMode` unless the gateway, the Local Agent or Apple Vision is on (`Views/OCRView.swift:1762`). The
pipeline then drops the per-page readers and the institutional import on the raw flag
(`OCR/OCRProcessor+Pipeline.swift:3198`, `:3202`). The Process Files cost pane's batch line and the settings strip's
also test the raw flag (`Views/OCRView.swift:897`, `:1031`; `Views/SettingsPanels/SettingsEstimateStrip.swift:146`),
though only the run's own model (`:3282`, `:3401`) tests `provider.supportsBatch`.

(2) OpenAI, GPT-5.4 mini as the run model, every page given a GPT-5 nano reader, four photos, redirected:

```
── s027-batch-off  estimate total=$0.0210              OCR calls by model: gpt-5-nano 4    "4 pages read by the reader their kind chose"
── s027-batch-on   estimate total=$0.0210 batch=$0.0105  OCR calls by model: gpt-5.4-mini 4
```

With the stored flag on, the run went standard (four direct chat calls, no batch) yet every page lost its reader and
was read by the run's model. The estimate's batch figure, $0.0105 against the $0.0210 the run is priced at, is what
the pane's batch line shows under the same condition. The pane itself was not drawn; that half is from the code.

(3) The settings panel says the toggle is disabled so that it "never promises a discount the run will not take", and
the pipeline's own comment drops the readers because "a paid batch is one model". Neither intends a run with no batch to
lose them. No owner question.
