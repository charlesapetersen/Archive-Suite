# W40.e7 — mutation sample on the irreversible paths

- **Date:** 2026-10-20. **Commit:** every run is at `aa8f0b82` (checkpoint 1, the runner) plus the runner's
  own later edits (output flushing, the `MUT_DRIVERS=all` switch, the SwiftPM object path), none of which
  touch app or package sources.
- **Runner:** `ops/verify/mutation-sample.sh <core|processor|notes|reader> [--check] [--only ID,…]`. The 50
  mutants, the text each replaces and what each breaks are listed in `ops/verify/mutation-sample.py`.
  Logs and a TSV of the verdicts are written to `$MUT_OUT/<area>/`, which was `/tmp/w40e7/` for these runs.
- **Environment:** the host. The unit bundles are headless (`ArchiveTestHost`) and the Processor drivers run
  headless. No corpus material is used: every suite and driver works in its own scratch or `mktemp` tree.

## How a verdict is reached

The runner works through the mutants one at a time. For each one it:

1. replaces one exact snippet in one source file (the snippet must occur exactly once);
2. rebuilds and runs the tests for that area;
3. restores the original bytes in a `finally`, keeping a copy in `.orig/`.

After the last mutant it rebuilds once more on clean source.

**The proof that a mutant landed.** The runner hashes the compiled object file of the mutated source and compares
it with the baseline object. A mutant counts as *survived* only when the tests passed **and** the object file
changed. If the tests passed and the object did not change, the verdict is `not-landed`. Every one of the 50
mutants changed its object hash; the hashes are in the TSVs, and each source's baseline hash is shown in the run
output.

**Proof that a mutant was reached.** Every survivor sits on a line the suite demonstrably runs:

- C02, C06, C07 and C12 share one `CoordinatedTagWriter.write` body with the killed mutants C01, C03, C04 and C05.
- C11 is in the removal path that every untag test calls.
- P01 and P02 are `trashOrRemove`, which Test 4 of the recovery driver calls directly.
- P06 is in the Clear path, which the recovery driver runs for every Clear.
- P08 and P12 are in `executePlans`, next to the killed mutant P07.
- P11 is in `move(_:to:fm:)`, which every filed output goes through.
- N05 is in `saveEntry`'s rename branch, which N04 shows is run.
- N11 is in `needsQuoting`, which every string field calls.
- R03 and R06 are in `applyOccurrence` with the killed mutants R04 and R05.
- R08 and R09 are in `undoLast`, which 15 Reader tests call.

So the survivors are not untested code. They are code the tests run but do not check.

**Which tests ran in each area:**

| Area | Tests run |
|---|---|
| core | the whole ArchiveCore suite (`swift test`) |
| reader | the whole `ArchiveReaderTests` bundle, without `DeepLinkTests` (a known environment flake) |
| notes | the whole `ArchiveNotesTests` bundle |
| processor | the three drivers that cover finalize and the Trash: recovery, manifest-persistence and merge-safety. The survivors were then run again against all 27 drivers that spend no money (`MUT_DRIVERS=all`, below). |

### Survivors — each is a missing test (S3)

| Id | Mutant | What no test checks |
|---|---|---|
| C02 | `FileIdentity.capture(target) ?? Optional(expectedIdentity)` | A write whose target has lost its identity (deleted or moved after discovery) must refuse. Only a replaced file is tested. |
| C06 | the verify-after-write of the tags always passes | Nothing makes the re-read differ from the write, so the `verificationFailed` path is never seen to fire. |
| C07 | the verify-after-write of the label always passes | The same gap, for the label. |
| C11 | `shouldRemoveTag` matches by `hasPrefix` | Removing subject `Smith` from a file that also carries `Smithson` must leave `Smithson`. The doc comment promises exactly this ("never substring"), and no test checks it. |
| C12 | `multisetEqual` compares sets | The verify must tell `["A","A"]` from `["A"]`. A test that calls the primitive directly would catch this. |
| P01 | `trashOrRemove` hard-deletes and returns `true` | Recovery Test 4 claims to check "not a hard rm". It checks only that the file left its path and that the function returned `true`, so a hard delete passes. It should find the file in the Trash (`resultingItemURL`), or inject a `FileManager` that records the call. |
| P02 | a failed `trashItem` returns `true` and leaves the file | No driver makes the Trash move fail, so neither the fallback nor its `false` return is checked. |
| P06 | `commitPreparedClear` accepts a mismatched token (`\|\|` for `,`) | A commit with a stale token must be refused. |
| P08 | `allFiled` ignores `failedMoves` | No driver has a run where every group files but a move failed. |
| P11 | an existing destination is hard-deleted, not trashed | The collision path in `move(_:to:fm:)` is not checked for where the displaced file goes. |
| P12 | a failed move counts as landed | No driver makes a move fail. |
| N05 | a rename onto an existing name is not disambiguated | The code calls this "defensive; one .md per dir by construction". It is reachable when a stray `.md` with the new title sits in the item folder. Plant one and rename. |
| N11 | a value with one edge space is written unquoted | The decoder trims, so a title `"Draft "` loses its space on reload. No round-trip test uses an edge space. W40.e6's fuzz did not generate one either. |
| R03 | the removal budget is the listed count, ignoring the pre-change count | Undo where a concurrent edit already removed one copy of a token that was added twice. W45's tests cover the addition side (R04 killed) but not this one. |
| R06 | the addition budget is never decremented | Undo with an addition budget strictly between 0 and the listed count, i.e. one copy re-added by hand since the change. |
| R08 | `undoLast` undoes the **oldest** group | None of the 15 `undoLast` tests has two undoable groups and checks which one was reversed. |
| R09 | `undoLast` skips the "inside the current archive" check | No test points undo at a file outside the current root. |

**The Processor survivors against every driver.** P01, P02, P06, P08, P11 and P12 were run again with
`MUT_DRIVERS=all`: all 27 drivers that spend no money, the same list as `sanitizer-runs.sh`. That took about 320 s
per mutant, after a green baseline of 323 s. All six still survived, and each object file had changed again
(`/tmp/w40e7-all/processor/processor.tsv`). So no part of the gate kills them, not just the three finalize
drivers.
