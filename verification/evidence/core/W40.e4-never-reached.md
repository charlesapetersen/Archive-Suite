# ArchiveCore: triage of 38 functions no run executed

Input: the ArchiveCore rows of the run union (the `.tsv` beside this file), from `core-unit` (507 tests),
the Reader's unit and UI chunks in the VM, every Notes unit and UI class in the VM, 55 key-free headless Processor drivers and the Processor UI tests in the VM. Method: for each function,
`rg -nw -t swift <base name>` over `ArchiveReader/macOS/Sources`, `ArchiveNotes/macOS/Sources`,
`ArchiveProcessor/macOS/Sources` and `packages/`, then a qualified search (`Type.member`, `.member(`) to drop name
clashes, and separately over the `Tests` folders. For Reader callers, the enclosing Reader function was looked up
in the Reader's never-reached list (`../reader/W40.e4-never-reached.tsv`): if it is absent there, it ran. Nothing was built or run.

**Caveat that changes the reading: the Reader runs barely count ArchiveCore.** The earlier input's `compiled_in` column
listed, for the ArchiveCore (non-UI) functions, only `core-unit, processor-drivers, vm-reader-ui-chunk4`: the
Reader unit chunks and UI chunks 1-3 did not attribute ArchiveCore code at all (the `ArchiveCoreUI` functions do
appear in Reader unit chunks 1 and 3 and UI chunks 1, 2 and 4). The proof that this hid real execution:
`ArchiveReaderTests/AdvancedSearchTests.swift:48-118` runs date rules through `AdvancedSearch.swift:174` and `:367`,
which call `AdvancedSearchText.dateBounds` and `.dateMatches`; the Reader functions ran, yet their ArchiveCore callees
were listed as never executed. The Notes runs have since reached those advanced-search rule helpers, so they no longer
appear here. Likewise `PageThumbnails.pageRoles` (calls `PDFPageRole.roles(of: CGPDFDocument)`) ran in the
Reader; `ContainerLevelsDraft.roleName` and `.preview`, listed here for the same reason, were reached once the Processor
UI tests joined the union. So for any function below with a Reader caller,
"untested" means only "no `core-unit` test and not reached in UI chunk 4 or the Notes runs". The coverage export for the Reader runs
should include the ArchiveCore objects (or the Reader's ArchiveCore must be linked so its counters land in the
measured binary) before these rows are acted on.

**Most notable findings.**
1. **Measurement gap, above: `PDFPageRole.roles(of: CGPDFDocument)` almost certainly ran in the Reader**, and several catalogue rows have Reader callers that ran. Fix the export, then re-derive
   this list; most Reader-reached rows will probably drop.
2. **Five dead functions:** `CatalogueAssociation.Pair.owner(of: DocumentReference, among:)`,
   `CollectionSettingsVocabulary.plain(_:)`, `ContainerLevelRole.field`, `ContainerBackfill.Directory.id`
   (an `Identifiable` conformance nobody iterates; the sheet only counts `scan.directories`) and the SwiftUI
   `TagChip.height(for:)`.
3. **`ScaleLaneCalibration` (3 functions) is a product-module yardstick used only by two scale tests**, which skip
   unless `ARCHIVE_SCALE_ROOT` is set (`CorpusWalkerScaleTests.swift:23`); no run set it.
4. **The suite's shared tag field `SubjectEntryField` never added a tag by a typed comma or Tab** in the runs
   (`tokenField(_:shouldAdd:at:)`). Leaving the field and `harvest` were reached by the Notes runs; Return was already
   exercised. This is the ArchiveCoreUI half, which the runs did count, so it is a real gap.
5. **Processor-only callers (3 functions) still read zero after the Processor UI tests:**
   `ItemTypeColors.isNone` (container backfill), `TagVocabulary.spelling` and
   `ImproveOCRSupportIdentity.suggestedLocation`. The UI tests reached the other three (`unreadableTags`,
   `levelMapURL(in:)`, `OCRPageKind.displayName`). The Notes runs reached the rest of the Notes callers; what still reads zero from Notes is the calendar picker's `DisplayCalendar.displayName`,
   `DateFieldEntry.sameDay` and the collection record rows.

No suspected bugs: nothing found while reading had enough evidence to claim one.
