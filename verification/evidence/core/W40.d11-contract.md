## How it runs

`ops/verify/cross-app-contract.sh <run folder> [core|reader|notes]`:

1. **Stage.** The run's Processor output (not the journey driver's `.txt`/`.tsv` bookkeeping) is copied with
   `ditto` to the rehearsal share, `processor-output/Archival Photos/RG 165 — War Department/`.
   `ops/verify/cross_app_contract.py expect` then writes what each PDF holds **without the suite's own parsers**:
   the tag xattr decoded with `plistlib` and sorted into facets by the SPEC's grammar, re-implemented from
   `SPEC/tag-format.md` §Tag facets; page 2 read with pypdf and its header split by the SPEC's layout; and the
   Reader's expected Document date, Read and Quality cells.
2. **core.** `ArchiveCoreTests/ProcessorOutputContractTests` (env-gated; real output is corpus-derived and never
   committed) reads every staged file through `TagReading.readTags`, `PDFHeaderParser.extract` and
   `ZoteroSource.gather` → `ZoteroExport.export`, and compares the raw tags, every facet, the colour label, page
   2's source name, provenance, Classification, Kind, date lines and item fields, the header diagnostics, and
   the date Notes would send to Zotero.
3. **reader.** `READER_JOURNEY=processed ops/gui/vm-gui-runner.sh reader xcuitest`: `make-journey-fixture.sh`
   copies the folder onto the guest disk (tag xattrs checked identical to the share's), then
   `ArchiveReaderUITests/ContractJourneyUITests` reads only. It waits for the content index to fill the Capture
   marker column, opens the Inspector, and walks the list row by row with ↓. Each row's Document date, Capture
   marker, Quality, Read, the item type beside the name, the token count in File tags, the Needs-attention cell
   and the Inspector's subject chips are compared with the expectation. Then it opens the last file and checks
   that the viewer's Preservation copy row finds the original that page 2 names.
4. **notes.** `W40D11_NOTES=1 NOTES_JOURNEY=integrations` runs only
   `IntegrationJourneyUITests/testD11_ProcessorOutputSourceBlock`. One dated Document Start (`00002 — RG 165.pdf`)
   goes into the Notes fixture's Reader corpus. The real Reader in the guest opens it and copies its page link;
   Notes pastes it as a source block; the block's Reveal opens the file in the Reader.

A VM step passes only on its test's own `passed` line and, for the Reader, on `read 113 of 113 rows; 0 with a
mismatch`, because a skipped UITest leaves `xcodebuild` green. The core step passes only on the test's own count
line for every staged file.

## Found on the way (test tooling, not the apps)

- The list's File tags token field reads in the accessibility tree as one U+FFFC per token, so the journey reads
  subjects from the Inspector's chips (`ar.tagEditor.chip.<subject>`) and only counts the cell's tokens.
- A first version left the list's row 0 out of view, so its click selected nothing. Home now scrolls the list to
  the top first. The Inspector raises the window's minimum width, so teardown closes it before shrinking the window
  back to the width it launched at.
- An independent read-only review (Opus) found ways the wrapper could report PASS without testing anything: a
  zero-test filter, or a skipped UITest. It also found gaps between the Python grammar and the SPEC: the file's own
  colour-name token, `Sent With Date Uncertain`, and non-field `Checked …` tokens. All were fixed before the
  recorded runs. The reviewer also noted that ArchiveCore reads `Date Uncertain` case-insensitively where the SPEC
  says "literal". Both sides agree and the Processor writes the exact form, so it has no effect here (no decision).
