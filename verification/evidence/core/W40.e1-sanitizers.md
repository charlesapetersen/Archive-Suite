## The runs can see a report (planted mutants)

A temporary test, never committed, with a data race (`concurrentPerform` incrementing a shared field) and a heap
overflow (writing index 4 of a 4-byte allocation) was added to each suite. Each one was run alone under each
sanitizer:

| Suite | TSan, planted race | ASan, planted overflow |
|---|---|---|
| Core | `WARNING: ThreadSanitizer: Swift access race`, exit 1 | `ERROR: AddressSanitizer: heap-buffer-overflow`, exit 1 |
| Reader | reported in the test log, `** TEST FAILED **` | reported, `** TEST FAILED **` |
| Notes | reported, `** TEST FAILED **` | reported, `** TEST FAILED **` |
| Processor driver | race planted at the top of `ManifestPersistenceTestDriver.run()`; written to `test-manifest-persistence.tsan.<pid>` through `TSAN_OPTIONS=log_path`, 14 report lines, runner exit 1 | not run (the plan asks for TSan only) |

The Processor case matters most, because a driver's own log is a `mktemp` the script deletes on exit. The runner
sets `log_path`, so the report survives in a file. The driver itself still exited 0 (TSan's default exit code is
not used by the driver scripts), and only the runner's count fails the run. `otool -L` confirms
`libclang_rt.tsan_osx_dynamic.dylib` is linked into the Reader and Processor binaries that ran.

## Finding: the Processor did not compile with TSan

The first TSan build of the Processor failed:

```
LiveCaptureProcessor.swift:1175:34: error: sending value of non-Sendable type
'() async -> LiveCaptureProcessor.StagedSegment' risks causing data races [#RegionIsolation::SendingRisksDataRace]
… note: access can happen concurrently   (line 1212, `texts: texts`)
```

`finalizeSegment` builds `var texts: [String]` and then captures the variable, not its value, in the
`Task.detached` that writes the segment's files. It then reads `texts` again after the `await`. The plain Debug build
accepts this, and the TSan build rejects it, presumably because the plain build's compiler turns the captured,
never-again-mutated `var` into a captured value and TSan turns that optimisation off. At runtime there is no race:
the only mutation (`texts.append`, line 1132) happens before the closure is made, and the actor is suspended at
the `await`. So this is a latent compile break, not a data bug. It is fixed with a capture list (`[texts]`), which
gives the same value the code had before. Checked: the plain Debug build has no new warnings, and the
manifest-persistence, recovery, filerelay, merge-safety and batch-resume drivers all pass on it. Then all 27 drivers
under TSan.

No other sanitizer report, and no other build break, was found, so nothing was filed under rule 5.
