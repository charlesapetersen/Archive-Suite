## Promise 1 — a crash or hang of our process in a VM run fails the run

Both VM entry points (`ops/gui/vm-gui-runner.sh`, `ops/autonomous/gui-vm-gate.sh`) mark the guest before the run
and copy every `DiagnosticReports` file newer than the mark (user and system directories) to the artifact share.
The fatal set is the tested app's process (which also prefixes its `<App>UITests-Runner`) and `xctest`, with
`.ips`, `.crash`, `.hang` and `.spin` reports. Other processes' reports and `.diag` resource reports are copied and
named but are not fatal. In the gate, a fatal report counts as a failed attempt, so the existing retry-once flake
guard applies.

**Real guest** — `ops/gui/vm-crash-harvest-probe.sh`, run twice (before and after the review fixes), 6/6 both times:

The probe compiles a trapping C program in the guest under each name. A trap (SIGTRAP) makes the guest's
ReportCrash write a real `.ips` to `~/Library/Logs/DiagnosticReports`.

**Classification (stubbed `tart`)** — `ops/autonomous/tests/prove-vm-lane.sh` §13, 95/95 for the whole file. It
covers these cases:
- a report from before the mark is ignored;
- our `.ips` and `.hang` are fatal;

## Promise 2 — the unit suites leak nothing of ours

`ops/verify/leaks-harvest.sh [core|reader|notes]`. ArchiveCore uses `leaks -atExit -- xctest ArchiveCoreTests.xctest`.
`-atExit` cannot be used on the app-hosted bundles: it injects with `DYLD_INSERT_LIBRARIES`, which replaces Xcode's
injector. Measured on the first attempt, the run failed with *"ArchiveNotes … encountered an error (The test runner
hung before establishing connection.)"* and `** TEST FAILED **` after 367 s. So each hosted bundle's principal
class, `LeakHarvestHold`, waits after the last test (only under `TEST_RUNNER_AS_LEAKS_HOLD=1`). The script then runs
`leaks <pid>` and releases the bundle with SIGUSR1. The hold fires after both XCTest and Swift Testing have
finished: in Notes, `[leaks-hold] pid=…` is the line straight after *"Test run with 969 tests in 95 suites
passed"*. MallocStackLogging=lite is on, so each leak carries its allocation stack.
`ops/verify/leaks-classify.py` counts a leak as ours when its stack has a non-entry-point frame in an `Archive*` or
`com.archive*` image (the test bundles are named by bundle id), or its tree names an `Archive*.Type`.

Triage of the 18 Notes roots (17 in the first run, plus one that appeared in the second run once the first fixes
were in). Every one was made by a test, not by the app:
- **16 roots: named pasteboards never released.** 7 `NSPasteboard` ROOT LEAKs and 9 `NSPasteboardItem` ROOT
  CYCLEs, created by `NSPasteboard(name:)` in `PasteboardPassageTests.namedPasteboard`, `SourceBlockPasterTests`
  and `NoteMetadataEditingTests` without `releaseGlobally()`. Fixed with a `defer` at each site.
- **1 root: `NoteBodyEditorModel` cycle** through `flushEditor.context`. `NoteBodyEditorModelTests` assigned a
  closure that captured the model. The app's own assignment (`NoteEditorPane.swift`, `[flushBox]`) has no cycle.
  Fixed with `[weak model]` in both tests.
- **1 root, second run: `NotesNavigationModel` ↔ `NotesModel` cycle** through `hardDeleteWindowHookForTesting`,
  set by `HardDeleteWindowTests` to closures that capture `env.nav`. Fixed by clearing the hook in `cleanup`.

The classifier was shown to fail on planted mutants: a frame renamed into `ArchiveCoreTests` gives 1, a tree type
renamed to `ArchiveNotes.NoteStore` gives 1, and a report with no `leaks Report` gives 2. A leaked string that merely
contains `/Applications/ArchiveNotes.app` stays 0.

The classifier cannot tell a product leak from a test that leaked, because in a unit run nearly everything is
allocated under a test. Each finding is therefore labelled with the test it came through and triaged by hand
(phase rule 5).
