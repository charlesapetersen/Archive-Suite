# W40.e4 — the coverage runs and what they measure

`ops/verify/coverage-gaps.sh` runs each suite with code coverage on and writes one normalised function list per run;
`ops/verify/coverage_gaps.py report` unions them. A function is **never reached** when every run that compiled it
counted 0. Test sources, generated files and compiler-made functions (closures, default arguments, thunks) are left
out, so an unreached closure inside a reached function is not counted here. Runs are kept in
`~/Library/Caches/ArchiveSuiteRehearsal/W40.e4/` until the item ships.

## What the method had to learn (measured 2026-11-26)

- **App-hosted unit bundles write no profile on the host.** The Reader's and Notes' signed, sandboxed test hosts
  left ProfileData empty, and xccov found no coverage archive. The VM's ad-hoc build writes it, so the unit bundles
  run in the VM.
- **Processor drivers need continuous mode.** `test-child.sh` stops a driver's app with TERM once the script has
  its report, which is before the app writes its profile at exit. In the first run 15 of the 28 drivers left no
  profile: each driver's `run()` read 0, and merge-safety, run alone and passing, wrote none. `%c` in
  `LLVM_PROFILE_FILE` maps the counters into the file as they change. With it the same 28 drivers reached 9,573
  functions instead of 4,943.
- **A plain `build` with `CLANG_COVERAGE_MAPPING=YES` writes profiles `llvm-profdata` refuses** ("number of
  counters is zero"). `build-for-testing -enableCodeCoverage YES` into the drivers' `macOS/build/DD` writes
  readable ones.
- **The driver list was too short.** It was sanitizer-runs.sh's 28 scripts. 27 more key-free scripts run the
  app's own driver and were added (55 in all).
- **The Reader VM runs carry almost no ArchiveCore coverage.** ArchiveCore's files are absent from the coverage
  archives of seven of the eight Reader runs (`xccov view --archive --file-list`); only `vm-reader-ui-chunk4`
  listed them. ArchiveCore's list therefore rests on `core-unit`, the drivers and that one chunk. The ArchiveCore
  triage marks the 9 rows the Reader certainly or very likely ran.
- **A stalled UI test costs its whole chunk.** Notes chunk 4 hung in
  `ChooseStoreFolderUITests.testChooseStoreFolderAdoptsAStoreThatSurvivesRelaunch` until the runner's stall guard
  ended it 1,502 s after the last output. A chunk ended that way writes no coverage, and the runner then waited
  20 minutes on the guest's shutdown. The runner's "293 test cases, the enumeration listed 1784" warning counts
  XCTest cases only: chunk 1 alone ran 361 Swift Testing tests. So the fourth chunk was run again without that
  class (`VM_SELECT`, `VM_TAG=rest`); the store-folder chooser rows it would drive are marked in the Notes triage.
- **`VM_SPLIT` deals whole classes.** The runner refuses a list of single tests under it, and the Processor's third
  chunk was single `ProcessorUITests` methods, so chunks 3 and 4 ran in one guest (`VM_SPLIT=0`, which
  `coverage-gaps.sh` now passes through).
- **The first three Notes chunks held only unit classes.** The 582 Notes functions listed before the re-run fell to
  97 once the UI classes ran: most of the Notes app is reached only through its window.

## Scope

- Not run for lack of time: the key-free journeys (the Processor's `reviews` journey and VisualReview, the Reader's
  `processed`, the Reader's ViewerSwitch fixture). The rows they would reach stay in the triage files, marked
  "gated" in the Processor's; a later run adds them with `coverage_gaps.py xcresult` (see the script's header).
- Left out by design: drivers and journeys that need a key, an account, a device or money (openrouter,
  segmentation-proof, local-segmentation-proof, smoke, tier2, drive-live, the phone legs, the `bulkocr` and
  `livecapture` journeys), and the Reader `rehearsal` journey, which uses the real-corpus sample.
- VisionOCRKit's own `swift test` suite runs a separate executable (`visionocr-checks`), so its coverage is not
  measured here. The figure above covers only what the Processor drivers reach.
- Branch coverage inside reached functions is a finer question than this item asks.
