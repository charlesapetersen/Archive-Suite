1. **Labels (all three apps, S3).** Text fields whose only name is their prompt (SwiftUI exposes it as a

2. **Contrast.** Every failure kept was measured from the screenshot (method below). The Reader and Notes fail in

   fainter style and measure **1.87:1 light, 2.20–2.26:1 dark**; that is under 3:1, the large-text floor, so it is
   filed S3, not S4. Screenshot check by eye: those lines are visibly faint.

## Four things the first runs taught, and what the helper does about each

1. **The audit covers the whole app, not the screen.** Run 1 reported the Reader's navigation window again on every
   later screen (49, 42, 76, 49 issues per screen in dark mode), and contrast failures for list rows the document
   window was covering. The helper now keeps only issues whose element is in the audited window's own tree, matched
   on type, identifier and frame against one snapshot, and reports each distinct issue once per sweep. A tooltip
   (`helpTag`) and the window's `touchBar` element fall outside and drop with it.
2. **Xcode's contrast verdicts do not hold up in the VM.** Measured from the screenshot: the Reader's file names
   that "failed" are 6.3–14.0:1, the window title 8.6–12.1:1, the fixture PDF's text 21:1; Notes' "Inbox" 7.4:1,
   a list date 14.9:1. In the final run the screenshot reproduced 7 of the Reader's 16 light-mode contrast issues
   and none of its 18 dark-mode ones; Notes 10 of 18 and 0 of 13; the Processor 4 of 7 and 3 of 5. So each contrast issue is
   measured (`ScreenPixels`: the commonest colour under the frame is the background, the pixel farthest from it in
   luminance is the text) and fails only below AA (4.5:1; 3:1 for text 24 pt or taller). Anti-aliasing can only pull
   the text pixel towards the background, so the measure errs towards failing. A frame not wholly on the window
   (Settings content scrolled below the pane) is not measured, and under 1.1:1 nothing is drawn under the frame at
   all — the Reader's "Tags in view" behind its preview sheet measured 1.01:1 — so it counts as covered.
   Cross-check: a separate PIL script over the same screenshots gave the same ratios (e.g. "Location" 3.95,
   "–" 3.23, the title 10.15).
3. **Notes could not be audited at all.** Every audit timed out (`Audit failed to complete in time`, error -56) on
   every screen, and the run then restarted the runner. A throwaway probe test bisected it in the VM: each audit
   type alone finished in 0.3–0.4 s except contrast, which timed out after 15 s and left every later audit in that
   launch timing out too, even with the main window closed. With `EditorTextView`'s two 1×1 DEBUG test probes left
   out of the tree, the contrast audit finished in 1.2 s. The audit test now launches with
   `-ANUITestNoEditorProbes YES`, which only it uses. Release builds carry no probes. The helper also runs each
   audit type on its own when the combined audit times out, and fails the screen naming the type that did not finish.
4. **Some issues are not the app's to fix** (shared exemptions, each with what it was seen on): AppKit's 14×14
   title-bar button group (parent/child mismatch); "Action is missing" on SwiftUI `Picker` pop-ups and `Menu`
   buttons — all eleven pickers in the three apps (eight in the Processor, two in the Reader, one in Notes), plain ones
   included, and three menus (the Reader's Saved Searches, Notes' New and heading menus); and unlabelled container groups whose contents are labelled (SwiftUI split panes, form and scroll
   containers, list rows holding a label and a count). Notes also exempts its UI-test harness strip
   (`an.editor.test.*`, `an.status.*`).

## The audit was shown to fail before its passes were trusted

Runs 1–4 went red on exactly the issues later filed: Reader run 1 had 8 failing screens; Processor runs 2 and 4
had 4 failures each, Notes run 4 had 4. Each passed only once its findings were filed as known issues, and every
exemption names the finding it covers. The "known issue no longer reproduces" path is the layout guard's rule and
was not exercised by a planted case here.

## What it cannot see

VoiceOver reading order, keyboard-only reachability across a task, and anything the audit does not model. Contrast
is measured once per screen, in the fixture's state; a hover or selection state not on screen is not covered.
